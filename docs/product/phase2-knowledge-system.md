# 个人知识系统方案骨架

Sep 29, 2026 · @YYuCChen

## 文档用途与目标

本文档是个人知识系统方案的骨架，记录讨论中已形成的共识，作为后续逐层细聊的依据，避免讨论变长后方向失真。

系统目标：让外部信息经过消化转化为自己的认知，再下透为方法论和技能，落地为行动，并由现实反馈回头修正。

衡量成败的标准不是收录了多少，而是认知是否真正改变了做事方式。

## 理论框架

三种基础范式的区别在于各自保留什么、丢掉什么，本方案让三者各司其职。

| 范式 | 保留 | 丢失 | 在本方案中的角色 |
| --- | --- | --- | --- |
| 图论 / 知识图谱 | 结构：谁与谁有关 | 语境、条件、不确定性 | 结构层 |
| LLM Wiki | 语境：原话与来龙去脉 | 精确查询、全局一致 | 内容层 |
| 本体论 | 类别与关系的约定 | 传统形式下的灵活性 | 以可修订约定的形式存在于规则文件 |

扁担比喻：图论和 LLM Wiki 是扁担两端，分别偏向结构和语境；本体论是扁担本身，决定两端挑什么、分几类。本方案采用竹制扁担：可弯曲、可修订，而不是一次定死。

吸收的前沿方法：

- 时序知识图谱：边带有效期，旧事实标记失效而非删除；区分世界时间（事实何时成立）和认识时间（我们何时这样认为）
- 超图：一条边连接多个参与者，每个参与者带角色，用于表达有条件的知识
- 类脑记忆：从问题涉及的节点出发，沿图扩散激活，找到隔几步才相关的内容
- 分层记忆与自主整理：工作上下文与外部存储分层，空闲时整理巩固
- 程序性知识封装（Skills）：管理怎么做的知识，平时只露简介，用时再展开
- 范畴论：不直接采用，只吸收三条原则：关系写精确、一致性写成约束、合并知识时显式写映射

## 场景画像

个人知识库，素材量小，核心在于认知的演化与下透。

| 维度 | 定位 | 对设计的影响 |
| --- | --- | --- |
| 规模 | 个人；素材量在上下文分界线以下 | 检索层、控制层可以很薄；lint 可全量通读 |
| 人数 | 单人 | 规则按个人习惯定；规则文件仍需写明，服务两年后的自己 |
| 主题 | 商业、生意经、社科、人情世故、AI、投资、健康 | 高度交叉；主题用标签和链接，不用文件夹层级 |
| 知识类型 | 认知思考、做事方法论、工作技能 | 与主题构成两个正交坐标 |
| 变化速度 | 以个人认知演化为主；AI 失效快，人情世故慢 | 结构层重点记录看法修订（认识时间）；按主题设复查周期 |
| 出错代价 | 整体可控 | 核查可轻；投资、健康两个主题的出处和推测标注从严 |

知识类型的定义：

- 认知思考：对事物怎么看。观点、判断、世界观，会随时间修订
- 做事方法论：一般该怎么做。可跨场景迁移的原则，必须写明适用条件与反例
- 工作技能：具体怎么做。针对特定场景、可直接操作

素材来源：

| 类别 | 内容 | 占比 | 性质 |
| --- | --- | --- | --- |
| 外部整理稿 | 社媒、博客、书籍经 ASR / OCR 转写，LLM 订正错字、分段、补作者日期来源，人工核查后落档 | 大头 | 他人观点 |
| 个人片段 | 文字或语音转写的独立想法，以及对现实世界的反馈；与 AI 对话中用户本人的发言也归入此类；想法常由素材引发，但与阅读时间存在随机跨度 | 小头，但分量最重 | 自己的认知与反馈 |
| 结构化数据 | 流水、账单、体检报告、健康记录 | 预留，暂不实施 | 客观的结果数据，时间序列 |

## 核心原则

以下十条已达成共识，后续设计不得违背。

1. 单向派生：原始素材是唯一事实来源，wiki 由素材编译，图由 wiki 抽取，永不反向修改。任一派生层损坏，都可从上游重建。
2. 原始素材只读：人工核查后的整理稿即原始素材，落档后永不修改。
3. 出处链：每条边、每个论断都能追溯到原始素材；追溯不到的一律标为推测。
4. 骨架先行：六层全部保留，每层先以最简形态部署并连通，再按需加厚。精简的是每层的厚度，不是层数；层间接口保持轻，便于修订。
5. 区分他人与自己：写成"某人认为……"，他人观点不得悄悄变成知识库的立场。
6. 推测可放开写：允许自由联想和假设，但必须标注，与有据内容分开。
7. 以落地衡量消化：一条认知是否被消化，看它是否变成了方法、技能或一次实际的决定。
8. 复盘由系统承担：不依赖用户养成重习惯，用户的习惯循序渐进地养成。

内容层讨论后新增两条：

9. 写入门控：认知与方法代表用户自己的观点，AI 只能提出候选，经用户确认后转正。
10. 状态靠计算：凡能从链接关系算出的状态，一律计算得出，不设需要维护的标记。

## 六层架构

六层各管一件事，全部保留，每层先以最简形态部署。时序知识图谱与超图合并为一张带时间的事件图，构成结构层。

&#91;embedded content: 六层架构 · 素材到 wiki 到图的单向派生\]

数据只从下往上派生：素材编译成 wiki，wiki 抽取成图；提问时在图上定位，再回到 wiki 读原文。

| 层 | 对应技术 | 负责的问题 | 最简部署 |
| --- | --- | --- | --- |
| 内容层 | LLM Wiki | 知识以什么形态存放 | markdown 文件夹 + 规则文件 + 索引页 |
| 结构层 | 时序知识图谱 + 超图 | 知识之间是什么关系，何时成立 | 页面元数据 + 带关系类型的链接（类型由所在小节决定），用脚本解析成图 |
| 程序层 | Skills | 怎么做的知识放在哪 | ingest、query、lint、confirm 四个 Skill |
| 检索层 | 类脑记忆 | 提问时怎么找到相关内容 | 从命中页面沿链接走一两步 |
| 控制层 | 分层记忆与自主整理 | 什么放进眼前，何时整理 | 规则文件与索引页常驻，其余按需读入；定时自动整理 |

三个关键流程：

- 读入：编写或更新 wiki 页面，同时抽出事件更新图；新旧事实冲突时，旧边标记失效而不删除
- 提问：先读索引挑出相关页面，再沿链接扩散，只把这些页面调入上下文，读原文作答
- 整理：定时 lint，合并重复、检查矛盾、标记过期、刷新主题页概览

原始素材的目录预留：

```
raw/
  外部/   人工核查后的外部整理稿
  自述/   个人想法、现实反馈、AI 对话中本人的发言
  数据/   结构化数据（预留）
```

## 下透链路与反馈回路

主要矛盾不是认知层膨胀，而是认知能否一步步下透到方法论和技能。下透的终点是行动与结果，并且必须有一条回来的路。

&#91;embedded content: 下透链路与反馈回路 · 5 个环节\]

没有回路，就无法知道下透是否成功；结构化数据和个人片段中的现实反馈，构成回路的起点。

落到结构上：

- 每一层都有向上和向下的链接：向上链接由写入者填写（方法来自哪些认知、技能来自哪个方法、实践用了哪个方法），向下链接由程序自动生成
- 最底层的技能不是一页描述，而是可直接拿来用的清单、模板、步骤，尽量写成 Skill
- 个人片段读入时区分想法与反馈；反馈关联到哪个方法由 LLM 推测、标为候选，用户确认后转正
- 结构化数据靠时间对齐：按采用某方法的时间点，对比前后数据，生成实践记录

lint 的检查重点：

- 悬空的认知：没有任何向下链接
- 未实践的方法：有方法页，但没有实践记录
- 长期不用的技能
- 被结果推翻但尚未修正的方法

## 内容层设计

内容层由八类页面组成，按类型分文件夹，主题只做标签；标题以页面回答的问题命名，保持稳定。本节结论已确认。

| 页面类型 | 回答的问题 | 说明 | 知识归属 |
| --- | --- | --- | --- |
| 来源页 | 这份素材讲了什么 | 每份外部素材一页 | 他人 |
| 概念页 | 这个东西是什么 | 名词：人物、组织、书、术语、现象；汇总各家说法 | 他人 |
| 认知页 | 我怎么看 | 以问题为题，页内写当前判断与演化 | 自己，需确认 |
| 方法页 | 一般该怎么做 | 可迁移的做法，含适用条件与反例 | 自己，需确认 |
| 技能页 | 具体怎么做 | 薄入口，内容只存在程序层的 Skill 中 | 自己 |
| 实践记录页 | 做了什么，结果如何 | 多由系统生成，用户确认 | 事实 |
| 综合页 | 某次提问得出了什么 | 查询的好答案回写，明确标为派生内容，必须带出处 | 派生 |
| 主题页 | 这个领域我知道些什么 | 七个主题各一页，作为导航和状况面板 | 汇总 |

另有系统页：index.md（总索引）和待确认.md（待确认清单）由脚本生成；log.md（变更日志，每条以统一前缀开头）和体检报告.md 由 AI 编写。

### 标题规则

- 标题是页面身份，永不改变；链接指向标题
- 认知页、方法页以问题命名，例如"谈判中面子的作用""合作谈判的开局顺序"，不以答案命名
- 观点写在元数据的"当前判断"字段和页内，随修订更新
- 概念页用名词本身；实践记录页用日期加事件；技能页用任务名；主题页用主题名
- 每页另有编号作为身份的最后保险
- 同一个问题只能有一页；看法分裂时，拆成两个更细的问题

index.md 每行格式：

```
谈判中面子的作用 —— 当前判断：面子是谈判里的隐性筹码（认知 · 已下透）
```

### 页面模板

```
认知页
  元数据：编号、主题、当前判断、确认状态、创建时间（已下透 / 悬空由链接计算，不存入页面）
  ## 当前看法
  ## 依据          来自素材 / 来自经历，均为链接
  ## 演化          按时间记录每次修订及其起因
  ## 推论到做法    向下链接到方法页
  ## 相关概念

方法页
  元数据：编号、主题、当前做法、确认状态
  ## 做法
  ## 来自认知      向上链接
  ## 适用条件
  ## 不适用条件
  ## 落地为技能    向下链接
  ## 实践记录      有效 / 无效 / 部分有效，各自链接

来源页
  元数据：编号、作者、平台、日期、类型
  ## 摘要
  ## 核心论点      一律写成"作者认为……"
  ## 引发的想法    链接到由它触发的认知页，可事后补上

概念页
  元数据：编号、子类、主题
  ## 定义          注明出处
  ## 各家观点      "某某认为……"，冲突时并列
  ## 我的相关认知  只放链接
  ## 相关概念

实践记录页
  元数据：编号、日期、主题、生成方式、确认状态（候选 / 已确认）
  ## 情境
  ## 做了什么      用了哪个方法、技能；不确定的标为推测
  ## 结果          有效 / 无效 / 部分有效 / 未知
  ## 事实依据      链接到原始片段或数据
  ## 影响          因此修正了哪些方法或认知

综合页
  元数据：编号、生成时间、触发的问题
  ## 结论
  ## 依据          每条结论必须链接到页面或原始素材

主题页
  ## 概览
  ## 核心认知      每行：标题 —— 当前判断
  ## 核心方法
  ## 常用概念
  ## 状况          自动统计：各类页面数量、悬空认知、只有外部观点的角落

技能页
  元数据：编号、主题、Skill 文件路径
  ## 用途  ## 来自方法  ## 执行文件  ## 使用记录
```

### 目录

```
wiki/
  来源/ 概念/ 认知/ 方法/ 技能/ 实践/ 综合/ 主题/
  index.md
  log.md
```

### 可信度机制

以下五条借鉴自社区 LLM Wiki 实践，已纳入内容层：

1. 格式由程序保证：编号、日期、类型等关键字段由工具自动填写或校验，不依赖模型自觉
2. 状态由链接计算：消化状态、悬空认知、未实践的方法等，一律从链接关系中算出，不作为需要维护的字段
3. 证据核验：lint 判定矛盾或过时时必须附原文引用，由程序核对引用确实存在，核对不上的判断丢弃
4. 写入门控：认知页、方法页、实践记录、技能及触发源关联，先以候选状态存在，经用户确认后转正；AI 不得替用户下结论
5. 回写防污染：查询的好答案存为综合页，标为派生内容，必须带出处，不得作为其他页面的原始依据

### 规则文件大纲

1. 目标与读者
2. 目录结构
3. 页面类型与模板
4. 写作规则：出处标注、他人与自己的区分、推测标注、单页长度
5. 链接规则：标题规则、每层的向上向下链接
6. 元数据规范（见结构层设计）
7. 操作流程（见程序层设计）
8. 修订记录

### 与社区 LLM Wiki 的对比

共同骨架：原始素材只读、wiki 由 LLM 维护、规则文件、ingest / query / lint、index.md 与 log.md。

本方案的主要推进：从结构上区分他人与自己；以下透到行动为终点，而非停在理解；程序性知识作为一等公民；页面身份稳定、观点在页内演化；设计之初即区分世界时间与认识时间；把提醒和复盘的人性因素作为设计问题。

不跟进的社区做法：数值化置信度（虚假精确，改用有据 / 推测 / 已验证的粗分级）；遗忘曲线（改用按主题复查加显式修订）；向量检索（当前规模不需要）。

参考：[Karpathy 原版 gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)、[rohitg00 LLM Wiki v2](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2)

## 结构层设计

结构信息全部写在 wiki 页面里，由脚本解析生成关系图。图是派生物，永不手动编辑，随时可重建。本节结论已确认。

### 元数据：按"由谁写"分三类

| 类别 | 谁来写 | 字段 |
| --- | --- | --- |
| 程序填写 | 脚本自动生成，LLM 不碰 | 编号、类型、创建时间、更新时间、确认状态（按用户答复写入） |
| 写入者填写 | LLM 直接填，用户发现错误时顺手改 | 主题、当前判断或当前做法、证据等级 |
| 计算得出 | 不存进页面，每次从图中计算 | 消化状态、是否悬空、实践次数、最近实践时间 |

认知页元数据示例：

```yaml
编号: C-0042
类型: 认知
创建: 2026-09-29
更新: 2026-11-03
主题: [人情世故, 商业]
当前判断: 面子是谈判里的隐性筹码
确认: 已确认
证据: 有据
```

各类页面的专属字段：

| 页面 | 专属字段 |
| --- | --- |
| 来源页 | 作者、平台、发布日期、素材类型、原始文件路径 |
| 概念页 | 子类（人物 / 组织 / 书 / 术语 / 现象） |
| 认知页 | 当前判断 |
| 方法页 | 当前做法 |
| 实践记录页 | 发生日期、生成方式、结果 |
| 综合页 | 触发的问题 |
| 技能页 | Skill 文件路径 |

证据等级分三级：推测、有据、已验证。页面级写在元数据中；段落级用段首的 \[推测\] 标记。

悬空的处理：已下透与悬空均由链接计算，不设储备字段（储备只是人为标注的悬空，已讨论不采纳）。lint 列出的悬空认知仅作信息展示，不视为待办，不催促。

### 用户确认：只确认一件事

用户只需确认 AI 写下的"你的观点"是否真是自己的观点。

- 触发时机：AI 推断出新的认知或方法；AI 认为某条看法有变，要修改当前判断或当前做法；系统生成实践记录
- 判断依据：读一句话，问"我是这么想的吗"，回答对、不对或改成什么。不需查资料，不判断对错
- 工作量：预计每周几条，每条几秒
- 方式：全部放入待确认清单，用户想看时再看，不主动推送
- 不确认的后果：内容保持候选状态，系统照常运转，AI 引用时知道它尚未被认可

### 链接类型：由所在小节决定

不引入特殊语法。链接写在哪个小节，就是哪种关系；正文其他位置的链接一律视为"提及"。约束：手动编辑页面时不得改动小节标题。

关系类型为封闭集合，新增类型需修订规则文件：

| 关系 | 方向 | 所在小节 |
| --- | --- | --- |
| 依据 | 认知 / 实践 / 综合 → 来源 / 实践 / 片段 | 认知页"依据"、实践记录页"事实依据"、综合页"依据" |
| 触发 | 来源 → 认知 | 来源页"引发的想法" |
| 来自 | 方法 → 认知 | 方法页"来自认知" |
| 落地为 | 技能 → 方法 | 技能页"来自方法"（方法页"落地为技能"为自动生成的反向视图） |
| 实践了 | 实践 → 方法 / 技能 | 实践记录页"做了什么" |
| 修正 | 实践 → 认知 / 方法 | 实践记录页"影响" |
| 反例 | 来源 / 实践 → 方法 / 认知 | 方法页"不适用条件"、认知页"演化" |
| 相关 | 认知 / 概念 → 概念 | 认知页"相关概念"、概念页"相关概念" |
| 提及 | 任意 → 任意 | 正文其他位置 |

### 双向链接：只存一个方向

- 向上的链接由写入者填写：方法写明来自哪个认知，技能写明来自哪个方法，实践记录写明用了哪个方法
- 向下的链接由程序自动生成：认知页的"推论到做法"、方法页的"实践记录"等小节由脚本重写
- 约束：自动生成的小节手动修改会被覆盖，要改就改另一端

### 事件节点：页面即超边

在当前规模下不设单独的事件存储。实践记录页、方法页本身就是带多个参与者的超边；需要额外处理的只有页面内部的演化记录，采用固定单行格式：

```
## 演化
- 2026-09-29 | 形成 | 面子只是礼节，谈判中应尽量忽略 | 起因：[[来源：某书]] | 已确认
- 2026-11-03 | 修正 | 面子是谈判里的隐性筹码 | 起因：[[2026-10 与某客户的合作谈判]] | 已确认
```

双时间的落地方式：

- 认识时间：即每条演化记录的日期，所有认知页和方法页都有，是个人知识库的主轴
- 世界时间：只对有时效的事实标注，主要是 AI 和投资主题的概念页；其他主题需要时再加

```
- 某公司的 CEO 是某某（有效期：2024 至今；记录于 2026-09；来源 [[来源：某报道]]）
```

### 关系图谱的生成

脚本读取所有页面，解析元数据、各小节中的链接和演化记录行，输出一个图文件：节点、带类型的边、事件，以及所有计算得出的状态。每次 ingest 或 lint 后重新生成，永不手动编辑，删除后可随时重建。

## 程序层设计

程序层由四个 Skill 组成，以一张权限表为底线。ingest 采用定时自动处理。本节结论已确认。

| Skill | 运行时机 | 职责 |
| --- | --- | --- |
| ingest | 每天定时自动处理新素材 | 把原始素材编译进 wiki |
| query | 用户提问时 | 基于 wiki 回答，好答案经同意后存为综合页 |
| lint | 程序检查每次 ingest 后；AI 检查每周一次 | 检查问题，能修的直接修，需要决定的列出 |
| confirm | 用户想处理时 | 处理待确认清单 |

### 权限表

| 类别 | 页面 | AI 的权限 |
| --- | --- | --- |
| 永不修改 | 原始素材 | 只读 |
| 直接修改 | 来源页、概念页、索引、日志、自动生成的小节 | 修改后记日志 |
| 候选待确认 | 认知页、方法页、实践记录、技能、触发源关联 | 只能提出候选，用户确认后生效 |

涉及"别人说了什么"，AI 可以直接写；涉及"我怎么想、我做了什么"，AI 只能提议。

### ingest：外部素材

1. 找出新素材：没有来源页的原始文件即为新素材，由程序计算
2. 建来源页：摘要；核心论点一律写成"作者认为……"
3. 更新概念页：新观点加入"各家观点"；AI、投资类时效事实标注有效期
4. 写入时检查冲突：与他人观点冲突则在概念页并列；与用户的方法冲突，在方法页"不适用条件"写一条带（候选）标记的反例链接；与用户的认知冲突，在认知页"演化"末尾追加一条候选修订。均不改动当前判断或当前做法
5. 更新索引、日志，重新生成关系图

外部素材永远不直接生成认知页；"我怎么看"只能来自个人片段。

### ingest：个人片段

1. 判断类型：想法、反馈，或都不是（如待办），后者忽略
2. 想法：全新看法生成新认知候选；印证已有看法则直接在认知页"依据"中补充证据（不改观点，无需确认）；改变已有看法则生成修订候选；同时在已读素材中寻找可能的触发源，作为候选关联
3. 反馈：推测关联的方法，生成实践记录候选并写明结果；结果与方法预期相反时，同时生成方法修订候选
4. 所有候选进入待确认清单

用户的录入习惯无需改变。

### query

1. 先读索引，再在关系图上从相关节点扩散，读取相关页面原文作答
2. 回答区分三种来源：用户已确认的观点、仍为候选的观点、他人的观点
3. 有保存价值的回答，AI 在末尾一句话提议保存，用户同意才存为综合页

### lint

程序检查（不用 AI，每次 ingest 后自动运行）：

- 断链、孤儿页、重复标题、元数据格式缺失
- 重写所有自动生成的小节
- 计算消化状态、悬空、实践次数等全部状态
- 核对每个出处链接确实存在

AI 检查（每周一次）：

- 矛盾：必须附原文引用，由程序核对引用存在，核对不上则丢弃
- 过时：AI、投资主题按复查周期检查，默认 3 个月
- 下透问题：悬空的认知、从未实践的方法、长期不用的技能、被结果推翻而未修正的方法
- 盲区：只有外部观点、尚无用户自己声音的主题角落

输出一份体检报告页，用户想看时再看；需要决定的事项自动进入待确认清单，其余由 AI 直接修复并记日志。

### confirm：待确认清单

所有候选汇总在一个页面，每条一行：

```
[3] 新认知 · 谈判中面子的作用
    推断：面子是谈判里的隐性筹码
    依据：10/12、10/20 的两条片段
    → 对 / 不对 / 改成……
```

用户在对话中直接回复，如"1、2 对，3 改成……，4 不对"，由 AI 落实。未处理的条目保持候选状态，不催促。

### 领域技能的产生

某个方法有 3 条以上"有效"的已确认实践记录、做法稳定后，AI 提议将其封装为技能（如从"合作谈判的开局顺序"提炼出"谈判前准备清单"），作为候选，确认后生成 Skill 文件。技能的使用情况又成为新的实践记录；超过 90 天未使用的技能在检查中列出。

### 运行方式

ingest 定时自动处理，用户无需发起。遇到想深读的素材，可随时要求"陪我读这一篇"，逐篇读入并讨论。

## 检索层与控制层设计

当前规模下索引可一次读完，因此两层都保持很薄，只预留升级接口。本节结论已确认。

### 检索：三步

1. 读索引：index.md 每行含标题与当前判断，AI 一次读完，挑出相关页面。这是主要检索方式
2. 沿链接扩散：从挑出的页面出发最多走两步；优先走依据、来自、落地为、修正、反例，最后才走提及
3. 关键词补充：人名、公司名、数字等精确信息用全文搜索补充。当前采用逐字匹配，天然支持中文；将来更换搜索工具时须专门测试中文

不引入向量检索。

同一机制的另两个用途：

- 找触发源：新想法进来时，在已读素材中找出最可能的几份，列为候选
- 查询覆盖统计：每次提问后记录读取了哪些页面（只记页面和日期，不记问题原文），供 lint 的盲区检查使用

升级信号与路径：索引过长导致 AI 漏掉明显相关的页面，或经常找不到记得存过的内容时，先由主题页承担二级索引，再引入专业搜索工具。

### 控制：放什么进眼前

- 常驻加载：规则文件、index.md
- 按需调入：检索找到的页面；仅在核对原文时调入原始素材
- 页面完整调入或不调入，不截断；单页长度上限保证这一点
- 不设"当前关注"页（已讨论，不采纳）

### 控制：何时整理

| 频率 | 内容 |
| --- | --- |
| 每天 | 读入新素材、程序检查、刷新待确认清单 |
| 每周 | AI 检查、生成体检报告、刷新各主题页概览 |
| 按主题周期 | AI、投资类内容的过时检查 |

以上均做成定时任务自动运行，具体时间在搭建时确定。不设遗忘或衰减机制。

### 新增素材来源：AI 对话

用户在与 AI 对话中本人说的话，作为个人片段读入；AI 的发言不算。读入后与普通个人片段走相同流程，生成的认知同样需要确认。

## 实施

方案已落地为两个文件：规则文件 AGENTS.md 和检查脚本 tools/kb.py。两者都与具体模型无关，Codex、DeepSeek 或 Claude 均可使用。定时任务不在此实现，由用户后续在所用工具中自行设置。

### 规则文件

- 文件名 AGENTS.md（Codex 等工具默认读取）；使用 Claude Code 时复制一份命名为 CLAUDE.md
- 内容按本方案展开：十条铁律、目录、八类页面模板、写作规则、链接规则、元数据规范、操作流程、检索规则、系统页格式

### 检查脚本

只依赖 Python 3.8+ 标准库，不调用 AI。每次写入后运行 python tools/kb.py：

1. 补填编号、类型、创建、更新；只有内容真正变化时才更新日期
2. 解析全部页面，生成关系图谱 .graph/graph.json（节点、带类型的边、演化事件、计算状态）
3. 计算已下透 / 悬空、实践次数、素材是否已处理等状态
4. 重写全部自动小节、主题页统计、index.md 和待确认.md
5. 程序检查，结果按错误、提醒、信息三级写入 .graph/检查结果.md

首次使用运行 python tools/kb.py init，建立目录、七个主题页和系统页。

### 实施中确定的细节

| 事项 | 结论 |
| --- | --- |
| 术语 | "图"统一称"关系图谱"，指记录节点与关系的数据文件，不是图片 |
| 索引与待确认清单 | 由脚本从页面内容生成，AI 不手写，保证与页面一致 |
| 单条链接的候选 | 触发源关联、反例在链接行末加"（候选）"，确认后删去标记，否决则删除整行 |
| 外部素材与用户认知冲突 | 在认知页"演化"追加候选修订，而非仅记反例 |
| 新增关系"相关" | 认知页、概念页的"相关概念"小节；概念页"我的相关认知"据此自动生成 |
| "落地为"的存储方向 | 由技能页"来自方法"写入；方法页"落地为技能"自动生成 |

| 已处理的判定 | 素材被任何页面引用，或路径出现在 log.md 中，即视为已处理；跳过的片段需在日志中记一行 |
| 标题字符 | 不得含 \\ / : \* ? " < > \|，冒号用全角 |

## 人性化设计

两条约束已明确：人不喜欢被推送；直面真实自己的复盘是反人性的，习惯需要循序渐进。本节结论已确认。

提醒方式：

- 搭车而非推送：只在用户本来就在互动的时刻顺带提问，不单独发起打扰（具体规则见下）
- 一次最多一个问题：可直接忽略，忽略后不追问、不累积
- 拉取优先：需要用户处理的事项集中在待确认清单，用户想看时再看，不定时推送
- 回答要轻：一句话即可，语音也行

搭车提问的具体规则（已确认）：

- 时机：只在用户提问时附在回答末尾，或在用户打开待确认清单时附在清单最后
- 数量：每次对话最多一个问题
- 相关才问：问题必须与当前话题相关，无相关内容则不问
- 忽略即可：不回答不追问，下次不重复
- 回答很轻：一句话即可；因用户在对话中的发言会读入为个人片段，回答自动成为实践记录候选，无需额外操作

示例：用户问"跟供应商谈价格要注意什么"，AI 答完后附一句"你之前记过'合作谈判的开局顺序'，最近有机会用上吗？"

这即是复盘阶梯第 3 级"一句话反馈"的具体形态。

复盘的阶梯，每一级何时进入由你决定：

1. 系统独做：从已有片段和数据中自动生成实践记录草稿，你什么都不用做
2. 一句话确认：偶尔确认系统推测的关联是否正确
3. 一句话反馈：愿意时对某个方法说一句管用或不管用
4. 主动复盘：对重要的事做简单回顾

语气原则：只记录事实和结果，不作评判；失败记录与成功记录同等对待。

## 风险与对策

已识别八项风险，七项对策已定，一项接受。

| 风险 | 对策 | 状态 |
| --- | --- | --- |
| wiki 与图两套表示不一致 | 单向派生，图可从 wiki 重建 | 已定 |
| 错误被自主整理和联想放大 | 出处链 + 推测标注 | 已定，与原有做法一致 |
| 六层复杂度过高 | 骨架先行，各层最简部署 | 已定 |

| 数据前后对比被误读为因果 | 页面如实标注只说明相关 | 已定 |
| 反馈稀疏且有偏，只记特别成功或失败的事 | 系统轻量询问部分弥补，不追求完整 | 接受 |
| 延迟触发的想法找不到源头 | 录入时顺手留线索；LLM 找候选触发源，标为推测待确认；找不到则链接到主题 | 已定，机制见检索层 |
| 结构化数据高度敏感 | 手动上传；是否上传由用户自行判断，上传即视为可以处理 | 已定 |
