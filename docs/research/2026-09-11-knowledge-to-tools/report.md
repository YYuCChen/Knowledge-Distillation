# 从「知识蒸馏」到「可用工具」：二期产品方向调研

调研日期：2026 年 9 月 11 日  
范围：GitHub 开源项目、OPC/FDE 公开社区、X、小红书、Reddit，以及相关研究与官方文档。  
性质：供产品讨论的研究材料，不是已经批准的二期方案，也不是对所列工具的安装推荐。

## 阅读指引

想先抓结论，读第 1、2、8、10 节；想看实际项目，读第 3、4 节；想理解电商例子怎么落地，读第 6 节；关心认知类知识与自我表达，读第 7 节。

本报告最核心的判断是：

> 二期不一定要从「知识蒸馏器」变成「Skill 生成器」。更值得探索的是：让已经收集的知识，在用户遇到具体事情时，变成可调用的方法、可核查的判断或可交付的成果。Skill 是其中一种载体。

## 1. 先说结论：跨越发生在哪里

### 1.1 不是从 Markdown 跨越到 Skill，而是从“内容产出”跨越到“任务结果”

当前的问题可以换一种问法：

- 内容产出：这位博主说了什么？有哪些精彩观点？
- 方法产出：他面对某类问题时，先看什么、如何判断、什么情况下不用这套方法？
- 任务结果：针对我这件事，哪些判断成立，缺什么信息，现在可以做什么？
- 反馈：做完之后发生了什么？方法应该保留、收窄还是撤回？

这四步不能互相替代。漂亮的摘要不等于方法，方法不等于适用于我，给了建议也不等于产生了效果。

GitHub 上已经能找到从书、视频、博主材料生成方法包的项目；也能找到把方法接到营销审查、翻译、练习、数据分析上的项目。但在本轮检索范围内，**没有找到足够完整、可独立核验的“蒸馏某电商博主 → 接入自己店铺 → 对照验证经营提升”的公开案例**。找到的是这条链路的不同段落，以及作者自述和演示。下面会分开呈现，不把拼接出的可行路径写成已经发生的成功案例。

### 1.2 Skill 有价值，但“把总结另存为 SKILL.md”没有自动增益

OpenAI 官方将 Skill 定义为任务专用的指令、资源及可选脚本组合；宿主先看到名称和描述，需要时再读取完整内容。它是运行时加载的方法，并不意味着模型已经被重新训练、永久吸收了这个专家的全部知识。[OpenAI：Build skills](https://developers.openai.com/codex/skills/)

因此，“AI 理解了老师”在产品上最好翻译成更可验证的表达：

> AI 在这次任务中，取用了哪些来源、遵循了哪些方法、做了哪些计算、形成了哪些推断？

这是可以展示和检查的；“复制了某人的大脑”则很难验收。

### 1.3 真正容易缺失的，是“我的情况”

同一套运营方法，面对新品和成熟品、低毛利和高毛利、库存充足和补货困难，可能导向完全不同的动作。把博主蒸馏得再完整，也不会自动获得你的经营目标、数据口径和约束。

营销工具库 marketingskills 的做法很直接：把产品、用户、定位等背景单独维护，具体任务再读取这个背景，而不是让每个 Skill 自带一套想象中的客户。[产品背景工作流](https://github.com/coreyhaines31/marketingskills/blob/5b2c0007766c6a1cf1d53fd8fc73e979e0821022/skills/product-marketing/SKILL.md)

**产品启发：二期可能需要的关键新对象不是更多标签，而是“一次应用”：用户现在要处理的事情、相关材料、约束、产出和反馈。** 这是研究后的建议，不是对现有架构的既定修改。

### 1.4 “实用”不必全部等于赚钱或自动执行

可以产生四类价值：

1. **交付价值**：少花时间完成一份可以使用的稿件、译文、检查报告。
2. **决策价值**：减少漏项，澄清假设，知道该补什么证据，避免草率行动。
3. **练习价值**：把“听懂了”变成做一次、获得反馈、再改一次。
4. **理解价值**：让一段模糊的自我表达，变成可以继续追问、比较和探索的问题。

最后一类也可以是工具价值，只是验收方式不是收入，而是用户是否更清楚自己在说什么、困在哪里，以及下一步想理解什么。

## 2. 不只一种出路：七种知识应用方式

以下是对项目样本的归纳，不是声称每种路线都已被证明有效。

| 路线 | 适合的知识 | 使用时补充什么 | 真正交付什么 | 最重要的验证 |
|---|---|---|---|---|
| 方法顾问 | 专家判断框架、策略、条件规则 | 当前问题、目标、限制、数据 | 诊断、备选方案、待验证假设 | 是否对应实际情况，而非套话 |
| 成果生产 | 写作、翻译、设计等方法 | 新素材、受众、格式要求 | 能编辑、使用的作品 | 正确性、完成度、修改成本 |
| 检查与审阅 | 标准、原则、常见错误 | 现有作品或方案 | 问题定位、证据、修改建议 | 是否找到真实问题，误报多少 |
| 练习与陪练 | 沟通、销售、学习方法 | 用户水平、场景、练习结果 | 练习题、反馈、下一轮任务 | 是否在新情境中做得更好 |
| 按需参考 | 事实、案例、观点、背景资料 | 当前问题 | 相关证据包、对照观点 | 检索是否准确，引用是否支持结论 |
| 小工具／流程 | 稳定计算、重复动作、判定规则 | 文件、字段、操作权限 | 表格、检查器、脚本、处理结果 | 可重复执行、数值正确、失败可见 |
| 经验复盘 | 自己做过的任务、纠偏、失败 | 实际结果及原因 | 修订后的方法、适用边界 | 新任务复用有效，而非记住旧答案 |

**关键区别：不是所有素材都应该生成一个新 Skill。**

一篇文章可以成为既有“方案审查”工具的参考材料；十段零碎观点可以在一次用户表达中被唤起；一本方法书可能只需要一个入口，按任务取用其中几项方法。只有反复出现、步骤相对稳定、确有独特帮助的任务，才更值得固化成独立 Skill。

接下来的案例说明这些区别。

## 3. GitHub：13 个项目，分别走到了哪一步

### 3.1 仓颉 cangjie-skill：从完整内容到可调用的方法包

**与需求的接近程度：很高。**

它不只生成读书摘要，还把材料整理为方法、案例、反例、触发情境、执行步骤与边界，再编译成单入口或较小的 Skill 包。仓库中确实有生成产物，不只有 README 示意。[项目与流程](https://github.com/kangarooking/cangjie-skill/blob/34e34bc5c7eb1c7d6cae9f84a9bcc62acb2a971b/README.md)

我重点看了《纳瓦尔宝典》的实际产物：统一入口按用户意图调用不同能力卡，包括判断训练、阅读、时间取舍等。因此，非专业操作类的认知内容，也能被转换成“遇到某类问题时的思考流程”。[生成入口](https://github.com/kangarooking/cangjie-skill/blob/34e34bc5c7eb1c7d6cae9f84a9bcc62acb2a971b/dist/naval-almanack-single/SKILL.md)、[判断训练卡](https://github.com/kangarooking/cangjie-skill/blob/34e34bc5c7eb1c7d6cae9f84a9bcc62acb2a971b/dist/naval-almanack-single/references/capabilities/judgment-training.md)

但这里要区分三层证据：

- 能看到文件和路由结构，说明方法包确实存在。
- 其 50 条路由评测明确标注为**静态自评、探索性**，不是宿主实际运行，更不证明决策质量提升。
- Token 基准是静态负载测量，不是业务效果测试。[路由评测说明](https://github.com/kangarooking/cangjie-skill/blob/34e34bc5c7eb1c7d6cae9f84a9bcc62acb2a971b/benchmarks/naval/phase1-routing-eval-50.md)、[基准口径](https://github.com/kangarooking/cangjie-skill/blob/34e34bc5c7eb1c7d6cae9f84a9bcc62acb2a971b/benchmarks/naval/metrics-v2/benchmark.md)

公开 issue 则补充了真实使用摩擦：有人希望提供执行演示；有人反馈生成太多技能后的目录负担；也有人报告编译引用断链，被发布校验拦住。这些是用户报告，未在本机复现。[使用入口问题](https://github.com/kangarooking/cangjie-skill/issues/14)、[技能膨胀问题](https://github.com/kangarooking/cangjie-skill/issues/20)、[断链问题](https://github.com/kangarooking/cangjie-skill/issues/30)

**值得借鉴：** 内容理解与发布载体分开；方法必须有触发和不适用情境；一个内容源不必裂变成几十个常驻技能。  
**不宜直接照搬：** 把每条启发都固化为命令。认知卡上的“每周留白一天”之类建议，还要经过用户条件校准，不能因为写进 Skill 就变成普适规则。

### 3.2 content-to-skill：从“总结主题”转向“定义一件工作”

这个项目的核心链路是：来源证据 → 可复用机制 → 执行流程 → 输出约定 → 验证信号。它要求明确谁在什么情况下使用、使用后发生什么变化，强调每步有输入、动作、产出和失败时的处理。[项目说明](https://github.com/gnipbao/content-to-skill/blob/ce5776a5161065836ed4647f9b96629d062ffdee/README.md)

它的评估表会区分“重述主题”和“真正定义了任务”，也区分“写了步骤”和“产出了可用文件／决策”。最高评价要求独立或前瞻验证证据，而不是模型觉得自己写得很好。[质量评估表](https://github.com/gnipbao/content-to-skill/blob/ce5776a5161065836ed4647f9b96629d062ffdee/references/evaluation-rubric.md)

**值得借鉴：** 蒸馏前或蒸馏后增加一句“这套知识可以帮助谁完成什么”。  
**证据边界：** 这是值得参考的生产规范，不是已证实的业务效果；项目自设评分也不能直接成为你的质量真值。

### 3.3 blogger-distiller：最像“蒸馏博主”，但目标需要辨清

它采集博主内容和互动信息，分析内容、策略和认知层，再输出给人阅读的报告及给 AI 使用的创作指南。其公开流程里，口播转写是可选增强项，不是每次都完整转录视频。[项目 README](https://github.com/otter1101/blogger-distiller/blob/167f21baadcb4b614a9a25268df8ca1e23e48ae7/README.md)

这里有一个会直接影响你二期方向的区别：

- **研究博主怎么做内容**：为什么这样起标题、组织论述、呈现案例。
- **研究博主教的专业知识**：他如何诊断店铺、处理库存、判断投放。

两者都能叫“蒸馏博主”，但所需证据不同。前者可以依赖内容结构及互动样本；后者必须读到他实际讲授的方法、前提、数据和例外。不能拿标题、评论和爆款表现代替专业内容。

**值得借鉴：** 人读报告与 AI 用指南分别交付。  
**证据边界：** 找到了分析流程，未找到足以验证经营提升的公开对照数据。

### 3.4 庖丁 paoding-skill：最值得借鉴的是“不急着认定规律”

庖丁也是博主拆解方向，但明确把观察、推断、置信度和验证状态分开；要求检查反例，不能因为高互动内容都用了某种写法，就认定该写法带来高互动。[项目说明](https://github.com/LearnPrompt/paoding-skill/blob/44a7c2b36bd70d9e71a695251a536370c43fba9c/README.md)

其验证规则尤其贴近你的风险：同一内容的截图、转写、转载不能当多个独立样本；已经看过的材料不能再声称是独立留出集；新题目上的普通稿与教练稿要使用相同任务，允许普通稿胜出。修订方法后，原来验证过的状态也不能无条件继承。[证据与验证规则](https://github.com/LearnPrompt/paoding-skill/blob/44a7c2b36bd70d9e71a695251a536370c43fba9c/skills/paoding/references/证据与验证.md)

**值得借鉴：** “可以生成，但尚未验证”应是正常状态；方法更新需要保留冲突与撤回。  
**证据边界：** 仓库提供的是流程和回归材料，不是已经证实能提高内容流量的实验。其样本数量门槛是项目约定，不是通用统计标准。

### 3.5 video-to-skill：教程不只转文字，还要能照着做

这个项目把视频语音、画面和时间信息结合起来，针对程序性教程提取操作步骤，并设计了由未看过原视频的执行者验证产物的流程。[项目说明](https://github.com/brenoepics/video-to-skill/blob/c527aa9b64cdb7e39a9d20dae6218c7cfc513473/README.md)

它的验证协议区分“通过、跳过、无法验证”，并要求隔离执行环境。比如依赖网络或真实账户的步骤，不能因为没跑就标成通过。[验证协议](https://github.com/brenoepics/video-to-skill/blob/c527aa9b64cdb7e39a9d20dae6218c7cfc513473/references/verification-protocol.md)

特别注意：仓库的 BENCHMARK 测的是合成音视频的处理耗时，而不是“任意教学视频能被正确转成技能”，更不是业务成功率。[基准测试口径](https://github.com/brenoepics/video-to-skill/blob/c527aa9b64cdb7e39a9d20dae6218c7cfc513473/BENCHMARK.md)

**值得借鉴：** 遇到“点这里”“看这个表”的视频，仅转文字会丢失关键证据；对于可执行方法，验收应尽量是实际完成任务。  
**不必现在就做：** 为所有内容新增完整视频视觉管线。可先识别“该内容依赖画面，当前证据不完整”。

### 3.6 marketingskills：看“使用端”比看“蒸馏端”更有帮助

它不是把某位博主视频一键转换的项目，而是面向具体营销工作的 Skill 集合。我核对了产品背景、转化率审查及其评测文件。[项目入口](https://github.com/coreyhaines31/marketingskills/blob/5b2c0007766c6a1cf1d53fd8fc73e979e0821022/README.md)

CRO 工作流先明确页面类型、转化目标、流量背景，再审查页面，最终交付优先修改项、测试想法、文案备选。这与“总结一本营销书”的输出完全不同。[CRO 实际指令](https://github.com/coreyhaines31/marketingskills/blob/5b2c0007766c6a1cf1d53fd8fc73e979e0821022/skills/cro/SKILL.md)

它也有测试提示词和预期行为，但许多断言检查的是有没有覆盖某项分析、有没有输出某个章节，而非实际转化率是否提升。[CRO 评测样本](https://github.com/coreyhaines31/marketingskills/blob/5b2c0007766c6a1cf1d53fd8fc73e979e0821022/skills/cro/evals/evals.json)

**值得借鉴：** 用任务命名入口；把稳定方法与用户背景分开；给出可编辑产物和待试验建议。  
**边界：** “格式完整、步骤遵循”只是合格底线，不能替代业务效果。

### 3.7 Tapestry / Ship-Learn-Next：不必生成新工具，也能把内容用起来

它把文章、课程或视频内容接到一个已有的行动规划流程：确定目标，选一个小的可交付成果，实践后记录结果，再调整下一轮。[项目说明](https://github.com/michalparkola/tapestry-skills/blob/80e1dc56df74d1cb849ad649c7ead9756e7929bb/README.md)、[实际行动规划 Skill](https://github.com/michalparkola/tapestry-skills/blob/80e1dc56df74d1cb849ad649c7ead9756e7929bb/ship-learn-next/SKILL.md)

例如学销售，不再只产出“销售十大原则”，而是形成一次可以完成并复盘的沟通练习。

**值得借鉴：** 不用给每篇内容造一个 Skill；“固定的应用方式 + 这次的知识材料”就可能有用。  
**边界：** 公开产物是计划与流程，并未证明用户长期学习效果。也不应强迫所有阅读都变成任务清单。

### 3.8 en-zh-max：专业方法进入生产流程的明确例子

该项目自述把叶子南翻译教材中的方法蒸馏后，接入文本分析、理解、初译、润色和检查等阶段，最终交付英中对照译文，而不是交付“翻译理论总结”。[项目说明与方法映射](https://github.com/3060226349kk-cmd/en-zh-max/blob/1675cbe1e814551c89d958981b2598360c8fdb05/README.md)

**值得借鉴：** 方法不一定成为一个独立顾问，也可以成为某项成果生产中的一个步骤。例如，来源里的“先识别受众”被用在写稿前，而不是另外输出一份受众理论报告。  
**边界：** 这是作者对方法来源和流程的说明，本轮没有逐页核对教材，也没有复跑译文盲评。多阶段、多重检查不天然意味着译得更好。

### 3.9 qmd：有些知识应该被检索，而不是被编成流程

qmd 提供本地文档检索，将关键词、语义检索和重排结合，并提供便于 Agent 取用的结构化结果与文档读取方式。[项目 README](https://github.com/tobi/qmd/blob/04e4dbd8245c527a88f1a8f0bda547aef9ca81fb/README.md)

它代表另一条路线：面对任务，从笔记里找到相关事实、案例和上下文，交给现成的分析工具使用。

**值得借鉴：** 时效事实、零散案例、不同作者的观点，不必强制改写为操作命令。  
**边界：** 检索到相关内容，不等于内容正确或推理正确。引用只是可追溯起点。此案例也不意味着你的二期必须立即建设向量数据库。

### 3.10 Fabric：复用“处理知识的方法”，而不是为每条知识造方法

Fabric 以可复用的任务提示模式处理输入材料，支持把内容加工步骤组合起来。[项目 README](https://github.com/danielmiessler/Fabric/blob/b682dad740f24e85ce9a48d23babc6780dd476ac/README.md)

**值得借鉴：** “从内容中找可实践的建议”“把观点转成待检验的问题”等操作，可以是产品自带的少量应用方式，用户只需选择材料。  
**边界：** 模式丰富不等于每个模式有效；它也不是对“蒸馏某专家后获得专业能力”的证明。

### 3.11 Vida archive：认知视角可以工具化，但人格模仿容易越界

仓库把公开归档内容与一个认知顾问 Skill 组合，列出心智模型、判断启发式和使用边界。实际 Skill 同时要求以作者身份和语气回应。[实际 Skill](https://github.com/superpilot69/vida-open-archive/blob/8b39b16f5db7fd1a253f9337362f3dcb9b864025/skills/vida-perspective/SKILL.md)

**值得借鉴：** 从非工具类表达里提炼“看问题的角度”，再用于一个新问题。  
**值得警惕：** “用这个框架审视”与“这个人会怎么做”不是同一件事。公开表达无法证明真实人格、全部经验或对新问题的立场。你的产品更适合标明“基于哪些公开观点的推演”，而不是冒充本人。

### 3.12 AutoHarness：从自己的任务结果里学习，而非只向外收集

它从工作会话中提炼可复用经验，并管理新建、合并、归档等生命周期。[项目说明](https://github.com/tigerless-labs/autoharness/blob/11d7b379187041ef353bce03fffaf994545b489b/README.md)

重要限制是：项目明确使用后续被调用／使用的信号，而不是独立留出任务得分来决定技能的存续。README 开头引用的其他研究提升数字，也不是这个项目自身的效果证明。

**值得借鉴：** 真实纠偏与失败比继续囤积文章更接近个人工具的改进来源。  
**边界：** 被调用多不等于判断正确；频繁使用也可能只是描述写得容易触发。用户表达、AI 推断和实际验证过的个人经验应继续分开。

### 3.13 Nuwa 小红书运营框架：一个重要反例——“很系统”未必“可信”

该仓库中有按账号阶段提供运营分析的 Skill，内容包括指标、阈值和决策流程。但一些精确权重或标准缺乏可直接核对的原始依据。[实际框架](https://github.com/Formangarden524/nuwa-distilled-skills/blob/f56d76ed9774f76d54a00474e4edcf7c1781483a/xiaohongshu-ops-framework/SKILL.md)

本轮不能据此断言这些数字一定错误；同样，也不能把它们当成已验证的平台规则。

**产品启发：** 最危险的产物可能不是粗糙摘要，而是“看起来像专业操作系统、实际上把猜测固化成数字规则”的工具。来源不足时，应输出“待验证假设”，而不是替用户补齐一整套精确标准。

## 4. OPC、FDE 与社交社区：哪些是案例，哪些只是信号

### 4.1 社区范围说明

“OPC 社区”“FDE 社区”并非唯一网站。本轮按公开可确认的入口调查了 OneOPC、FDE 中国社区、FDE 落地，以及 X、小红书、Reddit 的相关帖子。

OneOPC 的公开页面将知识库与实践社群分开，但具体实践讨论部分指向知识星球。本轮没有加入付费／私密社群，没有将其内部交流写成已调研内容。FDE 落地公开站主要呈现能力和业务服务入口，不能据此证明每类方案已获得效果。[OneOPC](https://www.oneopc.ai/)、[FDE 落地](https://www.fde.pub/)

### 4.2 FDE：比“万能蒸馏”更明确的是窄任务交付

FDE 中国社区的运营日报 Skill 页面写明输入数据、告警条件、责任人与推送方式，输出日报和流程材料。价值对象是日常运营动作，不是知识笔记。但页面的案例片段明确写了“示意”，其结果不能作为真实业绩；所链接的源码仓库本轮也未能公开取到。[运营日报页面](https://fdechina.ai/skills/ai-operations-daily)

另一篇选品实践介绍了“语义拆需求—脚本采集—AI 分析—人工筛选”的分工，交付报告和 Excel。它说明方法、脚本和人的判断可以组合，而不需要所有步骤都由模型完成。文章属于作者实践自述，未附业务提升对照。[瀚海方舟：选品 Skill 实录，53AI 转载](https://www.53ai.com/news/AIdianshang/2026070109475.html)

### 4.3 高价率运营工作台：最有启发的，是作者承认尚未闭环的部分

这篇 FDE 社区文章描述了把运营流程拆成业务 Skill 并建立评测的实践。更重要的是，它指出真实问题回流、修改建议的准确归因、决策日志积累仍有缺口；有模板不等于已经形成持续改进。其案例与效果属于文章自述，本轮没有取得生产系统或独立原始数据。[高价率运营 AI 工作台](https://fdechina.ai/cases/insights/ecom-ai-workbench)

**对你的启发：** 一次应用后，至少应该能保留“用户采纳了什么、为什么没采纳、后来发生什么”。否则工具只能不断生成建议，无法知道建议是否有用。无需照搬企业工作台的复杂工程。

### 4.4 社交平台的三个有用信号

- **小红书：蒸馏要解决问题，而非只模仿口吻。** “AI科技猎人”的帖子强调把认知方法用于调查、判断问题和下一步行动；这是使用主张，不是成效实验。[相关帖子](https://www.xiaohongshu.com/explore/6a79c603000000000502a04e)
- **小红书：专家价值往往在判断分岔。** LUCKYLEE 的销售负责人蒸馏帖讨论区分客户兴趣与购买能力。它提示我们应提炼判断依据，而非只整理销售话术；帖子没有公开可复跑的完整 Skill 和销售结果。[相关帖子](https://www.xiaohongshu.com/explore/6a1a50e8000000003501dd2d)
- **X：发布 Skill 之后还有“如何使用”的交付问题。** 仓颉作者介绍了面向非技术用户的在线使用入口，反映文件交付之外还存在体验层需求。相关商业效果是作者陈述，未独立验证。[作者帖子](https://x.com/i/status/2080540561870565525)

Reddit 中也找到 SkillsBench 作者传播评测结果的帖子，但它和论文是同一研究来源，不能算成第二份独立证据。[作者社区帖](https://www.reddit.com/r/ClaudeAI/comments/1r7jb7k/we_build_skillsbench_the_first_benchmarks_that/)

**综合判断：** 社区能很好地帮助发现痛点、使用方式和作品；它不擅长自动给我们可靠的效果证明。本报告没有用点赞量、Star 数或“有人赚钱了”来给路线排序。

## 5. 研究证据：为什么必须比较“有 Skill”和“没有 Skill”

### 5.1 SkillsBench：方法包能帮助任务，但效果取决于内容和任务

本轮核对的 v4 摘要报告：87 个任务、18 组模型与运行框架配置，人工整理的 Skills 使平均通过率从 33.9% 提升至 50.5%。这是该基准内的平均结果，不是你未来产品可承诺的提升。[SkillsBench v4](https://arxiv.org/abs/2602.12670v4)

早期 v1 的实验还报告：自生成 Skills 平均未带来收益，部分任务加入 Skills 后变差。**v1 与 v4 的任务数量和实验配置不同，不能把数字混成一个实验。** 也不能将特定自生成设置的结果扩展成“AI 永远不能蒸馏知识”。[SkillsBench v1](https://arxiv.org/abs/2602.12670v1)

### 5.2 SkillAxe：改进需要诊断“为什么没用”

这篇预印本尝试根据任务轨迹，分别检查方法是否产生帮助、触发是否准确、执行是否遵循、解决路径是否覆盖，再迭代 Skill。作者报告在相关基准中获得改进。[SkillAxe](https://arxiv.org/abs/2606.10546v2)

可借鉴的是诊断维度，而不是把论文效果数字当成电商收益。其研究环境、任务与评估方式不能直接代表你的用户场景。

### 5.3 SkillGLoW：可复用的通常是程序骨架，不是旧任务细节

这篇 9 月预印本把多次执行中的经验归并成程序家族，保留可迁移的流程，让每次任务重新生成实例细节，并通过实际执行检查改动是否退步。[SkillGLoW](https://arxiv.org/abs/2609.02217v1)

它支持一个值得测试的设计假设：**保留稳定方法，单独提供当前情境。** 但其结果仍是研究者在特定基准中的报告，不能证明视频专家蒸馏已经能完成业务迁移。

### 5.4 研究对产品最朴素的要求

不要只测“Skill 是否生成成功”。至少分开问：

1. **忠实吗？** 方法是否来自原材料，前提和例外有没有丢。
2. **适用吗？** 面对这个用户和任务，是否该调用它。
3. **有增益吗？** 是否优于直接让同一个 AI 处理同样任务。
4. **落地了吗？** 产物有没有被使用，实际效果和副作用是什么。

## 6. 把你的电商例子走完：从博主视频到一次可检验的应用

以下是基于上述案例综合形成的**假设性产品演练**，不是已经发生的店铺成功案例，也不包含对任何平台阈值的事实断言。

### 第一步：先选择要解决的问题，而不是“蒸馏这个人的一切”

相比“给我一套完整运营体系”，更可执行的起点是：

> 我想判断一个商品最近成交下降，下一步优先检查哪里，并形成一个低风险验证动作。

这不意味着材料只能围绕这个问题采集。可以广泛收集，但第一次应用应缩到一个可判断的任务。

### 第二步：将来源转成证据，而不只是转成摘要

假设老师说：“先区分流量变化和转化变化，再决定优化哪一环。”

保存的不应只是这句话，还应包含：

- 哪个视频、哪一段；文字是否核对过。
- 他讨论的是哪类商品、哪个阶段、什么经营目标。
- 这是明确建议、单一案例，还是模型根据多段内容的归纳。
- 他有没有讲例外、失败经历或相反情形。
- 同一作者后来是否修改观点。

涉及图表、后台演示、数字口径时，必须保留对应证据或标记缺失。模型补充的常识可以单列，不能冒充老师原话。

### 第三步：方法包要保存“分岔”，不只保存“金句”

一个候选方法可以长这样：

- 使用情境：成交变化诊断。
- 所需输入：可比时间段、流量、转化、商品与经营背景。
- 先做：核对数据口径、活动变化、缺失数据。
- 再做：区分已观察到的变化与可能解释。
- 分岔：不同现象对应不同的待查证原因。
- 不允许：仅凭一次变化断言原因；信息不够时自动填数。
- 输出：问题清单、证据、竞争性解释、下一步测试。
- 状态：来源支持，但尚未证明在你的店铺有效。

注意：这只是方法候选。专家说过，不等于因果关系已经成立。

### 第四步：应用时补充“我的情况”

用户可以先上传脱敏表格，不必第一天就接店铺后台。

| 类别 | 最小需要澄清的问题 |
|---|---|
| 目标 | 想提高成交、利润、周转，还是验证新品？ |
| 对象 | 哪个商品、哪个渠道、哪个时间段？ |
| 数据口径 | 访客、订单、支付、退款如何定义，是否可比？ |
| 经营约束 | 毛利空间、可接受预算、库存和补货限制是什么？ |
| 近期变化 | 价格、素材、活动、渠道、供应是否发生变化？ |
| 已做尝试 | 改过什么，什么时候改的，结果是什么？ |

老师的方法提供观察顺序；用户数据提供当前事实。两者不能混为一个知识库条目。

### 第五步：让模型做语义判断，让可靠计算处理数字

常见分工可以是：

- 脚本／表格：字段检查、时间对齐、汇总计算、异常值提示。
- AI：解释指标组合，指出多个可能原因，选择合适方法。
- 人：决定目标、判断不可量化限制、批准有经营风险的动作。

这是一种产品设计建议，不意味着需要立刻实现全套自动化。

### 第六步：交付“决策包”，而不是另一份长总结

理想输出只需回答几件事：

1. **确认发生了什么**：哪些数据变化可以核实。
2. **还不能确认什么**：缺字段、口径不一致、样本不足。
3. **可能解释**：至少保留合理的替代解释。
4. **为什么用了这个方法**：链接来源和适用前提。
5. **下一步动作**：先收集哪项证据，或试哪一个可控改动。
6. **如何判断继续或停止**：事前明确观察指标、周期和风险界限。

例如可以得出“当前证据不足以支持增加投放，先核对渠道构成变化”，而不是每次都必须给出一套增长策略。

### 第七步：使用后反馈，但不要过度归因

用户做完后记录：实际执行了什么、没执行什么、为什么、观察到什么。

一次改善可能同时受到活动、竞争、季节和库存影响。方法有效性与结果变化需要分别判断。好的工具允许“本次无法归因”，也允许撤回最初建议。

**这条完整链路里，Skill 只负责一部分：组织并引导方法的使用。** 数据、权限、工具调用、结果反馈不会因为生成 Skill 就自动具备。

## 7. 那些认知类、碎片化知识，到底能做什么？

### 7.1 不必预先知道用途，可以在问题出现时被激活

一条关于“激励影响行为”的观点，在收藏时未必有明确用途。但当你描述一次合作中的困惑时，它可以变成检查问题：

- 双方想要的结果是否一样？
- 谁承担成本，谁获得收益？
- 当前行为有没有另一种解释？
- 哪些只是我的猜测，需要向对方确认？

此时它的产出不是一个专业操作 Skill，而是更清晰的分析。**用途可以晚于收藏出现。**

这也是按需参考、认知顾问与固定应用工作流值得保留的原因：不用在入库时强迫每条信息证明自己的生产力。

### 7.2 四种可以做成具体体验的认知用途

以下为设计推演，不是已经验证的用户研究结论。

| 用户带来的东西 | 知识如何介入 | 适合的产物 |
|---|---|---|
| 一个模糊想法 | 找相近概念和不同解释 | 问题澄清卡、概念区分 |
| 一个坚定判断 | 找支持、反例和适用边界 | 论证检查、待查证清单 |
| 一次困惑或经历 | 提供几种有出处的观察角度 | 多视角对照、后续追问 |
| 一段想表达的话 | 辅助组织论证、补证据、找反驳 | 保留本人立场的表达草稿 |

这里真正的价值不是“AI 永远劝你行动”，而是让你看见之前没分清的东西。没有行动产物，也可以完成一次理解任务。

### 7.3 你的“主体—客体”灵感，应该成为边界而不是装饰

你的表达是这次理解活动的出发点；第三方材料是参考，不是替你定义自我的权威。

一个可能的体验是：

> 你说：“我总觉得产品还像玩具。”  
> 系统先帮助区分：你担心的是用户不复用、没有明确交付，还是价值无法验证？  
> 然后从已有材料找几种不同的产品价值观，说明各自照亮了什么、漏掉了什么。  
> 最后由你确认哪种解释贴近本意，而不是自动认定“你是一个结果导向的人”。

这至少要求分开保存：

- 你的原始表达及发生情境。
- 外部来源的观点。
- AI 对两者关系的解释。
- 你认可、否定或暂不判断的部分。

**尤其不能把一次表达直接升级为稳定人格、信念或偏好。** 自我探索需要允许矛盾、变化和未定论。

### 7.4 什么不适合硬做成工具

纯审美体验、文学感受、尚未理解的疑问、一次偶发情绪，都可以只被保存和再次阅读。

二期增加应用能力，不应反过来把一期的阅读价值判成无效。“有目的地用”与“无目的地遇见”可以共存。

## 8. 对你的二期，三种产品形态的真实取舍

这里的排序是基于本轮研究形成的讨论建议，不是用户已经批准的路线。

### 方向 A：可交给外部 AI 使用的“应用包”

用户选材料和用途，产品生成带来源、方法、输入说明、示例及限制的包；先交给 Codex 等现成工具使用。

优点是可以快速验证“这份蒸馏是否真的改善任务”，不用先重建一个完整智能体平台。代价是用户仍需理解如何带入数据、触发使用和反馈。

**适合验证：** 方法蒸馏本身有没有独特价值。  
**不够的地方：** 只增加下载按钮，可能重演“生成了但不知道怎么用”。

### 方向 B：围绕“一件事”的应用工作台

用户不是先选 Skill，而是说“我想检查这份方案”“帮我理解这段想法”“用这些材料写一稿”。系统选择相关知识，询问缺少的背景，产出结果并收集反馈。

优点是用户路径完整，也更能容纳你的自我表达构想。代价是需要明确任务状态、数据边界、证据呈现和使用反馈，产品设计范围比单纯导出大。

**适合验证：** 用户是否会为了处理具体事情而回来。  
**不够的地方：** 如果所有入口最终都只是长篇聊天，仍然可能缺少可验收结果。

### 方向 C：自动执行的垂直工具

选择一个稳定任务，例如批量检查、固定报表或数据整理，把方法、脚本和外部系统接起来。

优点是完成标准明确、节省操作可测。代价是数据连接、平台变化、权限和错误后果显著增加，也容易让项目变成某一行业的专用软件。

**适合验证：** 已知高频流程的效率和可靠性。  
**不宜直接跳到：** “蒸馏完任何人就能自动替我经营”。

### 我的倾向

**先用 A 验证方法的增益，用少量 B 的入口验证用户是否真会使用；暂不把 C 当作通用二期的前提。**

这样可以把两个尚未被证明的假设分开测：

- 这份知识是否让 AI 做得更好？
- 用户是否愿意经常把真实问题交给这个产品？

如果第一条不成立，界面再完整也无济于事；如果第二条不成立，Skill 再精致也可能继续躺在仓库里。

## 9. 最小验证：怎么知道它不只是一个更漂亮的玩具？

### 9.1 先选容易比较的任务，不一定先选电商经营

首次试验可以选择你自己能够判断质量的工作，例如：

- 根据蒸馏出的表达方法，审阅一份自己的稿件。
- 根据某套产品方法，检查一页功能方案。
- 根据某课程，形成一次能实际完成的练习。
- 用同一套运营方法分析脱敏的历史场景。

电商最终收益很重要，但首次验证未必需要承担完整经营系统的变量与成本。

### 9.2 三组对照，比“看起来不错”更有信息量

对同一批新任务，提供完全相同的用户背景和数据：

| 组别 | AI 获得什么 | 主要回答的问题 |
|---|---|---|
| A | 好的普通任务提示 + 用户背景／数据 | 强基线能做到什么 |
| B | 同样输入 + 可访问的相关原始材料 | 增加知识本身有什么帮助 |
| C | 同样输入 + 蒸馏方法包及其必要引用 | 组织成方法是否比直接给材料更好 |

尽量固定模型、工具权限、运行预算和评审标准，记录实际耗时与成本。每组使用独立上下文，避免答案串流。不能故意给 A 一个很差的提示词来制造提升。

若原文太长，必须明确比较的是“相同预算下的检索原文”和“方法包”，而不是掩盖上下文截断。不同预算的比较也可以做，但结论应写成质量—成本取舍。

### 9.3 评价什么

- 是否出现事实错误、编造数据、错误引用。
- 是否真正利用了用户背景。
- 是否发现关键问题，而不是输出更多常识。
- 是否给出能采取的动作或能直接使用的产物。
- 是否保留不确定性、合理反例和不适用边界。
- 用户需要花多少时间修改或核查。
- 是否值得在下次同类任务中再次使用。

评审时尽可能隐藏组别；允许普通 AI 胜出。先用少量任务找明显失败，再决定是否扩大，不能用几个例子宣称统计显著。

### 9.4 还要测“该不该用”

加入几类容易误用的任务：

- 缺少关键数据。
- 作者方法已经过时或与新材料冲突。
- 只有相似关键词，实际问题不属于该方法。
- 用户目标与作者默认目标不同。
- 来源包含绝对化建议、无法核对的阈值。
- 用户要求超出授权的自动操作。

能正确说“这次不适合”“还缺证据”，也是工具能力，不是失败。

### 9.5 面向产品的结果指标

相比“蒸馏多少条”“生成多少个 Skill”，更有意义的候选指标是：

- 用户启动了一次真实应用，而不只是打开笔记。
- 产物被使用／采纳，或明确帮助排除了一项方案。
- 下一次同类问题再次使用。
- 使用中节省的时间与额外核查负担。
- 错误建议、误引用与撤回的记录。
- 用户能否解释这次为什么有帮助。

这些是待验证指标，不是本轮调研已经测得的数据。

## 10. 二期值得保留的设计原则

### 10.1 给人看的与给 AI 用的，是两种视图，不是两个真相

“知识库是给 AI 读的，人只看 PDF/PPT/Doc”有启发，但不宜照字面当产品定律。

人也需要阅读来源、检查论证、修改方法；AI 也未必需要整个知识库。更稳妥的设计是：

- 来源和事实保持可追溯。
- 面向 AI：明确含义、适用条件、引用和任务输入。
- 面向人：呈现结果、理由、限制、可修改项。
- 两者来自同一条证据链，避免各自改写后互相矛盾。

Markdown、JSON 或 PDF 都只是表示方式。结构好不好，关键在信息关系，而非扩展名。

### 10.2 稳定方法、当前数据、个人立场分开

方法包不应写死某家店的订单数字；一次店铺应用不应修改原始来源；AI 根据你的表达推测出的立场不应自动成为“你认同的知识”。

你现有项目对来源、AI 衍生内容、用户认知的身份区分，是二期可以继续利用的基础，而非需要推翻的障碍。

### 10.3 多来源不等于平均成“一套正确答案”

两个老师的建议相反，可能来自不同目标、阶段、资源和风险偏好。工具应显示冲突及各自前提，让用户知道自己选择了哪套假设。

同一个人十年前与今天的观点，也不宜无提示地合成一个永恒方法。

### 10.4 更新知识，也要知道哪些应用会受影响

不一定先建设复杂版本系统，但至少应能回答：

- 这份方法来自哪些材料、哪个版本？
- 新材料支持还是推翻了旧结论？
- 哪些建议使用过旧方法？
- 旧结果需要重新检查吗？

这是让工具长期可信所需的基本可追溯性。实现范围可以在具体场景确定后再定。

### 10.5 不把来源内容当成执行授权

外部视频、文章或生成方法中出现“上传全部文件”“运行这个命令”，不应自动成为你的系统指令。原材料进入的是证据边界，不是权限边界。

同样，“给我下一步策略”不自动包含改价格、发消息、下单或支付的权限。

### 10.6 公开可读，不等于适合重新分发

借鉴代码和流程之前，需要分别核对项目许可、素材来源以及拟分发的内容范围；本轮没有完成这些项目底层语料的授权审计。不要因为代码仓库有许可证，就把它解释为全部书籍、课程和博主内容都可重新打包发布。

## 11. 回到你最初的问题

我不认为你必须从“启发人”彻底转向“替人干活”，才算从玩具变成工具。

更准确的变化可能是：

> 过去：我把内容交给蒸馏器，得到一份值得阅读的东西。  
> 二期：我把正在经历的问题、想表达的东西或要完成的任务交给它，它调用合适的知识，帮助我形成更清楚的理解、更可靠的判断，或者一个能用的成果。

你的电商例子属于“方法顾问 + 数据分析”；翻译属于“成果生产”；检查方案属于“审阅”；从自己的表达出发探索属于“理解与反思”。

这些不应一口气全部做。它们的共同底座也不应被过早设计成庞大的通用系统。

**最值得先验证的一个问题是：同一件真实事情，有了你的蒸馏结果，用户是否比直接问 AI 获得了更好的帮助？**

如果能稳定回答“是”，再决定把它装进 Skill、应用工作台还是垂直工具，就会更有依据。
