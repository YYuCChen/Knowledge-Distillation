# 测试与证据

## 不同证据回答不同问题

- 单元与合成夹具测试证明指定代码行为。
- 集成检查证明声明环境中的组件协作。
- 原生冻结包检查证明对应平台打包与运行行为。
- 真实来源/模型测试只覆盖实际使用的素材、服务和环境。
- 人工阅读与浏览器检查验证普通断言难以证明的表达、交互和视觉。

模拟模型调用不证明真实服务可用；Mac验证不证明Windows；旧通过数量不证明当前checkout通过。将源码提交、命令/场景、环境、结果及未验范围记录在一起。

## 已有自动化

`.github/workflows/quick-tests.yml`在符合条件的PR或手动触发时运行选定隔离回归，刻意不安装全量项目/模型依赖，JUnit产物保留3天。它不是完整产品/双平台发行验收，也不是秘密扫描工具。

行为变更先覆盖相关失败和预期行为，再按影响扩大验证。保留能捕获缺陷的测试，不能靠删测试或缩窄需求制造通过。

纯文档修改检查事实、状态、链接与隐私，不为此安装全量模型依赖；明确哪些测试没有运行及原因。

## 保护数据

显式指定新的测试数据目录，使用合成或获准再分发的夹具。迁移、媒体清理、凭据迁移和结果导入脚本存在，不构成可以对私人应用目录运行的授权。

清理测试现场前，保存最小复现方法、有价值的失败结论和未决问题。真实用户内容、服务返回和数据库副本不能作为公共CI日志或默认公开夹具。


## 工作纪律（2026-09-13用户裁决）

1. **先明确验收对象与硬要求。** 开始任务时确认目标、交付物、当前基线、用户约束和完成条件；识别直接依赖与容易遗漏的入口。关键缺失或冲突会改变方向时，只暂停依赖该决定的工作，并提供已查清的选项；其他必要工作继续。

2. **核对实际状态，并维持唯一权威。** 不把文件名、配置声明、旧报告、默认设置或现有环境当成实际状态。核对真正使用的数据、版本、账户、运行环境和最终产物。共同要求集中维护；有意保留的差异须说明理由、适用范围和验证依据。实验、候选、正式与历史状态明确分开。

3. **把每项重要要求对应到证据。** 验收必须说明检查了什么、针对哪个对象和环境、结果是什么、仍缺什么。区分通过、失败、未验证和不适用，不能用总通过数、构建成功或局部样例代替完整覆盖。适合自动判定的硬要求应有失败门禁，并验证错误输入确实不能通过。

4. **验证用户真正会走的流程。** 按改动影响覆盖实际使用环境，以及首次使用、可选功能、重启、升级和失败恢复等相关路径。给用户执行入口前完成可代做的预检，确认编码、路径、权限条件和真实退出状态；只有无法代做的部分才交给用户验证，并准确说明局限。

5. **维护来源、身份与内容含义。** 区分用户决定、来源事实、模型提议和 Agent 推断。涉及引用、数字、单位、否定、条件与归属的处理要有对应依据；格式正确或相似不能代替正确性证明。错误修复、规范化和重试不得悄悄降低要求、改变原意或把未知写成确定。

6. **完成必要关联变更和生命周期处理。** 修改一项要求时，检查受影响的代码、配置、依赖、数据规则、缓存、安装升级、文档和交付入口。保留有用进度，限制失败范围，控制重复执行。新版可用后核实旧组件是否仍能被误用，再按归属退役；无关问题可提醒，不擅自扩大范围。

7. **按现有授权保护资料与操作对象。** 使用独立测试数据；实际写入、发布或清理前确认对象、权限、唯一资料、在用状态及恢复条件。已有明确授权的必要工作直接完成，不反复索要批准；新范围或重大取舍交给用户。按精确范围操作并读回结果，不以移动、备份名称或脚本退出码代替实质验证。

8. **发现错误后纠正结论，并留下防复发检查。** 证据不足时明确说出缺口；不要把间接线索写成确定的成功或阻塞。新证据推翻旧结论时，同步更正当前状态和相关交付，保留必要历史。交接说明最新裁决、证据、未决项和写入范围。严重返工后补上能发现同类偏差的检查，不只增加提醒性的口号。

项目运行时基线和生命周期门禁见 [Python运行环境契约](python-runtime.md)；数据保护与精确退役范围继续遵守 [存储规范](storage.md)。非Python组件明确标为不适用并验证其实际功能，不伪造解释器版本。
