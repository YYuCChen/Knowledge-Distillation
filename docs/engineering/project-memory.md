# 项目资料的归档与公开

代码基线和产品记忆共同支撑后续开发。源码以公开仓库核验后的分支为起点；用户的未来意图、未决问题和历史取舍不能由版本号替代。

## 资料放在哪里

| 资料 | 去向与要求 |
|---|---|
| 源码、测试、依赖声明、构建脚本 | 源码仓库；使用合成或可再分发夹具，不能夹带本机配置和真实用户数据 |
| 当前产品/工程规范 | `docs/product`、`docs/engineering`；行为改变同步更新，避免多套平行正文 |
| 已决定待做事项 | `docs/roadmap/next-version.md`；问题、决定、状态和验收条件可追溯，未做不能写完成 |
| 远期构想与未决问题 | `docs/roadmap/exploration.md`；标明用户原意、候选建议与开放问题，保留原始依据 |
| 有价值的原始讨论、历史裁决、设计推演 | 经内容审阅后进入 `docs/history`；保留角色、原文与替代关系；原件和摘录明确区分 |
| 自有调研报告与来源索引 | `docs/research`；保留日期、证据深度与局限，不整包分发引用来源的全文/视频 |
| 安装包与必要升级资产 | Releases及发布流程要求的资产位置；不塞入源码提交，不随意删除仍被更新器引用的文件 |
| 本机配置、密钥、账号/浏览器状态 | 公开仓库之外；模板只留无真实值的示例 |
| 实际使用的知识数据、数据库、Vault、原始媒体、真实案例运行记录 | 本地及用户选择的可信备份；不得因为藏在文档、日志或截图中就转为公开 |
| 环境、模型缓存、重复包、下载分片、临时构建与测试现场 | 验收后清理可重建且无活跃引用的副本；保留必要版本/下载依据和小体积结果 |
| 未筛查的混合旧目录 | 本地保护，不整包上传或按年龄清空；提取明确价值后再核对精确清理范围 |

用户同意公开项目资料，意味着可以审阅后公开构想、讨论、设计和技术结论，不应再将这些全部默认归为私人资料。与项目无关的私人谈话和实际知识数据仍排除；公开某份讨论不等于公开其全部附件、元数据或引述的第三方原文。

## 收尾顺序

1. 找出新增或改变的用户决定、原始构想、未决事项、失败经验和唯一文件，先落档。
2. 确定每份材料是当前规范、历史原文、摘录还是建议；写明来源、日期、状态和公开处理方式。
3. 检查精确提交文件及新增提交历史中的配置、凭据、真实内容、截图和隐藏文件；不能只靠扩展名或ignore。
4. 检查引用、来源对应、公开版删改和未实现状态，记录必要摘要；重要原文不能只剩一句过度概括。
5. 经PR交付并确认远端保存后，按任务授权清理可重建临时目录。唯一原件或混合目录的删除另需完整去向核对，公开成功不自动等于准许删除。

同磁盘保全不是异机备份。源码、公开文档上传完成，也不能据此宣称实际知识数据和密钥已有灾难恢复能力。自动清理只适合边界明确的临时产物；本规范不创建无人值守删除服务。
