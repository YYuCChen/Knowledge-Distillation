# raw 接口规格

状态：v1，依据 [决策0004](../decisions/0004-phase2-alignment.md)（2026-09-29）。本规格是**应用**与**wiki 维护 Agent** 之间唯一的接口：应用按本规格写入，Agent 与 `tools/kb.py` 按本规格读取。改动本规格须同步修订 vault 守则与 kb.py，并保持向后兼容。

标【不可逆】的条款必须严格做到；其余为默认做法，可以按工程需要调整，但要在交付中说明。

## 1. 原则

1. **raw 是知识库正本。** 只凭 vault 就能重建知识库（wiki 与关系图谱）。应用数据库只记录加工过程。
2. **【不可逆】只进不改。** raw 文件一经写入，任何程序（应用、Agent、kb.py）都不修改、移动、删除它。需要订正时，写一个新文件取代旧文件，旧文件保留。
3. **只洗净、切配，不调味。** raw 里只有原件和客观事实：谁的、从哪来、什么时候、怎么取得、切成了哪几段。不写摘要、观点、概念、评价。
4. **写入的是完成品。** 素材只有在识别疑点处理完、身份确定之后，才写入 raw。还在处理中、待用户核对或身份待定的素材，留在应用里。

## 2. 目录与文件名

```
vault/
  raw/
    外部/YYYY/MM/<编号>.md      第三方素材
    自述/YYYY/MM/<编号>.md      用户本人的话
    数据/…                      用户手动上传的结构化数据（第 5.3 节）
  附件/raw/<编号>/…             raw 素材所附图片
  知识蒸馏器/                   V1 来源笔记（阅读版，不属于 raw）
  wiki/  tools/  .graph/  AGENTS.md  CLAUDE.md   维护侧（见 vault-kit）
```

- 放在哪个目录，由身份决定：本人的话进 `自述/`，其他一律进 `外部/`。
- `YYYY/MM` 取**收录于**的年月（本地时区）。
- 文件名就是编号，不含标题。原因是标题里可能有空格、冒号等字符，会破坏路径引用。

## 3. 编号【不可逆】

- 格式：`R-YYYYMMDD-NNNN`。日期取收录于的本地日期，`NNNN` 是当天的顺序号，从 0001 开始。例如 `R-20261012-0003`。
- 编号由写入方分配，与内容无关，永不改变，也永不复用。
  - 应用分配时，以数据库计数为准。
  - Agent 写入（第 5.2 节 AI 对话）时，用 `python tools/kb.py raw-id` 取号；它会扫描 raw 现有文件，取当天最大号加一。
- 应用在数据库中记录 `material_id → 编号, 路径` 的映射，保证同一素材只写一次。

## 4. 文件结构

### 4.1 信封（YAML frontmatter）

字段名使用中文，与 vault 守则一致。

| 字段 | 必填 | 说明 |
|---|---|---|
| `编号` | 是 | 见第 3 节 |
| `格式版本` | 是 | 本规格版本，当前为 `1` |
| `身份` | 是 | `第三方` / `本人` / `本人附言`（附言指对某份材料的补充说明，如"这篇重点看后半段"） |
| `标题` | 是 | 来源标题；随手记可取正文开头约 20 字 |
| `作者` | 否 | 第三方作者或账号名；本人素材固定写 `本人` |
| `渠道` | 是 | 抖音 / 小红书 / 知乎 / 微博 / X / YouTube / B站 / 网页 / 直接文本 / PDF / EPUB / Markdown / 图片 / 飞书文字 / 飞书语音 / AI对话 |
| `原链接` | 否 | 规范化后的原始链接 |
| `产生于` | 否 | 内容本身产生的时间（作者发布时间、说话时间），ISO 8601，带时区；平台只给日期时只写日期（如 `2024-09-18`）；不知道时省略 |
| `收录于` | 是 | 进入库的时间，ISO 8601，带时区 |
| `取得方式` | 是 | 取得原件用到的工具、模型和版本，例如 `{采集: douyin, 识别: qwen3-asr 1.2, 应用版本: 2.0.0}` |
| `去杂` | 否 | 删掉了哪些非内容部分，只写类别和位置说明，例如 `结尾关注引导 1 处` |
| `订正` | 否 | 识别订正列表，每项写 `{片段: source-3, 原识别: "…", 订正为: "…", 方式: 用户核对}`。**【不可逆】原识别必须保留在这里** |
| `身份判定` | 本人素材必填 | `{结果, 依据: 规则/模型名, 置信度, 用户改判: 有/无}` |
| `邻接` | 否 | 捕捉时窗口内（默认前 30 分钟）同一入口先到的素材：`[{编号: R-…, 间隔秒: 1020}]`。只记之前的，之后的由后来者记，两边合起来就是完整的邻接关系。**【不可逆】必须在写入时记录** |
| `附言对象` | 本人附言必填 | 附言针对的素材编号 |
| `取代` | 否 | 本文件修订了哪份旧 raw 的编号（第 6 节） |
| `应用记录` | 否 | 回溯到应用数据库用，例如 `{material_id: 50, knowledge_result_id: 50, 来源笔记: 知识蒸馏器/xxx--kr-50.md}` |

### 4.2 正文

- 正文是规整后的原件：Markdown，UTF-8，LF 换行。
- **【不可逆】切分到段落，每段后面紧跟一行块编号**：

```markdown
第一段原文……

^source-1

第二段原文……

^source-2
```

- 段落切分沿用 V1 的规则：以空行分段；代码块、表格不拆开（见 `v1/markdown.py` 的 `_source_blocks`）。这样 V1 笔记里的 `^source-N` 与 raw 的 `^source-N` 指向同一段。
- 音视频转写：有时间码时写在段首，如 `[00:12:03] ……`。没有时间码不强求。
- 对话类素材（如 AI 对话）按发言轮次分段，段首写发言人，如 `**本人**：……`。
- 图片放在它在原文中的位置：`![[附件/raw/<编号>/image-1.jpg]]`，下一行写 `^image-1`。
- 正文里不出现任何摘要、标签、评论或"AI 认为"。


## 5. 三类素材

### 5.1 外部（应用写入）

- 时机：V1 流水线生成 `source_facts` 后（疑点已处理），在发布 V1 来源笔记的同一阶段写入 raw。raw 写入失败不影响 V1 笔记发布，但必须如实记录失败并可重试。
- 正文取自 `source_facts.snapshot`，不从 V1 笔记反推。
- 订正来自来源审查记录（`source_review_results` 等）。无法可靠还原原识别时，写 `订正: 未保留逐处原识别`，不编造。
- 飞书里粘贴的大段第三方文本，按现有"直接文本"流程进入这里。

### 5.2 自述（本人的话）

**飞书随手记（应用写入）**：
- 遵守[飞书随手记需求](../roadmap/handoff-feishu-capture.md)的全部【不可逆】条款。
- 捕捉当时就把原始记录存进应用数据库（不可修改）。raw 文件在身份确定、识别疑点处理完之后写入。
- 身份待定的消息只进应用待办，不写 raw。
- 录音在疑点处理完后按媒体生命周期释放，raw 里只留转写。

**AI 对话（维护 Agent 写入）**：
- 只保存用户本人的发言，`渠道: AI对话`，按发言轮次分段。
- 例外：处理 `wiki/待确认.md` 时，用户回复的“对”“改成……”或“不对”及其理由属于操作指令，不另存为 `raw/自述/`；确认结果写入对应知识页，操作摘要写入 log（见[决策0004 的 2026-09-30 裁决](../decisions/0004-phase2-alignment.md#6-真实使用后的知识库工作流裁决2026-09-30)）。
- 用 `kb.py raw-id` 取号；只新建文件，不改已有文件。

### 5.3 数据（用户手动上传）

- 用户自己把文件放进 `raw/数据/`，格式不限（CSV、PDF 等），应用不参与。
- 可选：同名 `.md` 信封文件，写明来源和时间。二期不做进一步规范。

## 6. 写入规则

- 原子写入：先写临时文件，再重命名；复用 `v1/publisher.py` 的 no-clobber 做法。
- 【不可逆】目标文件已存在时不覆盖。内容相同视为已写入；内容不同报冲突，交给人处理。
- 需要订正已写入的素材时（例如后来才发现识别错误）：写一个新编号的文件，信封写 `取代: 旧编号`，旧文件原样保留。wiki 以最新的为准。
- 同一素材重复投递：沿用已有编号，不写新文件（V1 的 `materials` 去重规则）。
- vault 不可用时：暂存在应用里，恢复后补写，不丢素材。

## 7. 存量迁移

- 一次性工具，从 V1 数据库把已有的 `source_facts` 导出为 `raw/外部/` 文件。
- 编号按原 `materials.created_at` 分配，`收录于` 取原收录时间。
- V1 来源笔记与 vault 中已有文件一概不动。
- 必须先在复制出的测试数据与测试 vault 上跑通，再由用户授权对正式 vault 执行。

## 8. vault-kit 与 kb.py 适配

以下改动随本规格一起交付，放在本仓库 `vault-kit/`：

1. kb.py 识别 `raw/…/编号.md#^source-N` 形式的段落引用：判定"已处理"和检查引用是否存在时，去掉 `#^…` 后缀再比较，并核对该块编号确实存在。
2. kb.py 新增 `raw-id` 子命令（第 3 节）。
3. kb.py 读取 raw 信封，在检查结果里列出待处理素材的标题和身份，方便 Agent 分批处理。
4. vault 守则（AGENTS.md）：
   - 铁律 1 补充"Agent 只可按 5.2 新建 AI 对话素材"；
   - 出处写法改为引用到段落（`raw/…/编号.md#^source-N`）；
   - 同名异义概念页用括注区分；
   - 取代关系以最新文件为准；
   - 待处理素材的来源说明改为指向本规格。
5. 新增 vault 根目录的 `CLAUDE.md`，只写一行，指向 AGENTS.md。
6. 新增快捷命令：处理新素材、体检、确认、陪读。先按用户实际使用的 Agent 写法提供，其余可逆。

## 9. 验收

- 全部测试使用独立、可丢弃的数据目录与测试 vault，不碰正式数据（仓库 AGENTS.md）。
- 应用侧覆盖：
  - 各渠道外部素材写入格式正确；
  - 订正信息完整保留；
  - 重复投递不重复写入；
  - 目标已存在时不覆盖；
  - vault 暂时不可用后能补写；
  - 取代写法；
  - 随手记的身份判定与邻接记录；
  - 身份待定时不写 raw；
  - 存量迁移可重复执行且结果一致。
- 维护侧覆盖：kb.py 能识别段落引用和取代关系；在测试 vault 上完整跑一遍"处理新素材 → 确认 → 体检"。
- 交付时分开报告合成测试、真实飞书收发和真实 Agent 维护的结果，不以其中一种冒充另一种。

## 10. 应用侧实现说明（第 1 阶段，2026-09-29）

本节说明应用如何按上文写入 raw/，以及交付时做出的可逆取舍。代码在 `v1/raw.py`、`v1/raw_migration.py`。测试在 `tests/v1/test_raw.py`、`tests/v1/test_media_lifecycle.py`。

**时机**：来源事实成立后、提炼知识之前写入（`Distiller._finish`）。知识提炼失败或不合格时，素材照样进入 raw/。raw 写入失败只记录，不阻断 V1 笔记发布。`应用记录` 写入当时已知的 `material_id`、`source_fact_id`；知识结果和来源笔记路径只在写入时已存在（如存量迁移）才写。

**索引与编号**：
- schema 20 新增 `raw_records`，记录编号、主体、身份、相对路径、确切字节、附件清单、取代关系与写入状态，以及每日计数 `raw_counters`。编号、路径、内容写入后由触发器保护，不可改、不可删。
- 新编号取数据库计数与 vault 内当天已有最大号两者中的较大者再加一，避开 Agent 用 `kb.py raw-id` 已取的号。
- 已知边界：vault 暂不可用期间应用已分配、但尚未落盘的号，Agent 看不到；若随后产生同号文件，写入会以 `raw_id_collision` 拒绝并留待人工处理，不覆盖。

**写入**：
- 先写附件，再写正文文件。每个文件都先落临时文件，再用硬链接放到目标位置：原子，且永不替换已有文件。
- 目标已存在：字节相同视为已写入，不同则记 `raw_target_conflict`，文件原样保留。
- 路径上有符号链接时拒绝写入。
- vault 不可用时记录保留在数据库里，工作线程每分钟补写一次，补写的字节与分配时相同。

**媒体**：
- 图片按原文位置嵌入 `附件/raw/<编号>/image-N.<扩展名>`，下一行写 `^image-N`。
- 没有定位到文字的图片放在正文之后，不丢弃。
- 应用内已释放字节的图片不编造，只在信封 `未保留附件` 中列出成员编号。
- schema 20 起，平台原图只有在该素材的 raw 及附件已写入后才允许释放（`media_lifecycle.RELEASABLE`，数据库触发器同样把关）。因此未配置 vault 时原图会一直保留在应用内。

**信封**：
- 字段顺序与名称同第 4.1 节。自由文本、链接等值用 JSON 字符串形式的双引号标量，仍是合法 YAML，`kb.py` 按行解析即可读回。
- `订正` 来自来源事实中保存的纠正记录：用户核对、用户订正（选中文字改写）、模型修复，每项保留原识别。
  - `片段` 按偏移或唯一出现位置定位，拿不准写 `未定位`，不猜。
  - 新增可选字段 `存疑`：用户选择"无法确认"的片段。
- `取得方式`：
  - `识别` 写平台字幕、当时配置的语音识别、Apple Vision 引擎与系统版本，或 Docling 版本。
  - 存量迁移不知当年模型，写"语音识别（未记录模型）"，应用版本写"未记录（V1 数据库）"，并加 `导出: V1 数据库存量导出`。
- `标题` 依次取来源标题、平台原生标题、原平台描述首行、提交文件名，都没有时取正文开头约 20 字。
  - 直接粘贴的文字没有文件名，取正文开头约 20 字（第 3 阶段端到端试跑发现此前误用了占位名"直接文本"，已修复）。
- `产生于` 按平台原值换算：知乎的秒级、小红书的毫秒级时间戳，X、微博的英文日期，ISO 时间；YouTube 只有上传日期，写日期。此前知乎、小红书、YouTube 会漏写，在一份 V1.3 数据副本中涉及 57 份里的 20 份，已在正式迁移前修复。

**取代**：`RawLedger.supersede` 为同一主体分配新编号，写入新文件并在信封中写 `取代: 旧编号`，旧文件原样保留，`current()` 返回最新一份。取代文件的 `收录于` 取取代发生的时间。

**从 vault 重建索引**：应用启动后首次补写前，扫描当前 vault 中带 `应用记录` 的 raw 文件，把索引里缺少的补进来（来源记为 vault）。因此在 V1.3 上先做了存量迁移，升级到 2.0 后，同一素材沿用迁移时的编号，不会重复写入。没有 `应用记录` 的文件（Agent 写入的 AI 对话）不进应用索引。

**存量迁移**（第 7 节）：
- 命令：`python -m knowledge_distiller.v1.raw_migration --data-dir <数据目录> --vault <Vault> [--dry-run] [--report 结果.json]`，打包应用用 `KnowledgeDistiller --migrate-raw --data-dir … --vault …`。
- 应用在运行时拒绝执行。数据库只读打开，不改结构：schema 19（V1.3）上运行后，V1.3 照常可用；只有 schema 20 才同时写入索引。
- 编号按 `materials.created_at` 分配，已在 vault 中的素材跳过。再次运行不新增文件；同一份数据的另一副本产出逐字节相同。

  - 写出 57 个 raw 文件、3 个附件；原有 60 个文件和数据库字节都没有变化。
  - 第二次运行计划为 0；另一副本产出相同。
  - 57 个信封都是合法 YAML；有来源笔记的 56 篇，`^source-N` 与 V1 笔记完全一致。
  - 保留订正 206 处（25 处未能定位到段落）、存疑 8 处、未保留附件 5 个。
