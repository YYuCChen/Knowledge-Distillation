# 组件发行与恢复

Windows 模型存储及程序基座解压、差量重建、目录校验、安装复制与回退清理使用扩展路径支持深层目录。路径转换不解析链接，原有重解析点拒绝规则继续执行。固定 Docling 版本的 Tableformer 配置读取在适配层规范化分隔符，保留实际文件路径与模型哈希，不修改系统长路径策略。导入成功不能代替冻结成品的 PDF/EPUB 转换验证。

本文说明施工分支已实现的协议。正式版本和线上可用入口以发行验收记录为准；本地候选构建不表示已经发布。

每个平台有固定程序基座，两个平台共用 Docling 模型资产。签名 JSON 清单绑定平台、CPython 契约、源码提交、目标程序身份、固定基座、模型身份及直接差量。新安装组装模型＋基座＋一份基座到目标的差量；已安装且身份匹配时只取当前版本到目标的直接差量。已有模型逐文件核验后复用。没有匹配路径时明确提供修复路径，不遍历差量链或暗中回退下载旧式完整包。

Mac 直接差量使用固定 Sparkle BinaryDelta，重建后核对程序树并执行严格代码签名检查。Windows format 2 的每个文件明确为 reuse、full 或 HDiffPatch 文件内补丁，核对基线、载荷及输出哈希；format 1 保留读取兼容。收益比较采用整文件实际压缩体积，补丁收益不足时在已签名计划中选择 full。解码器在独立进程运行，限制时间、内存和输出，Windows 在恢复进程执行前挂入限额 Job。原生真实业务两版构建的收益、还原和故障结果必须单独验收，不能用随机字节样本代替。

`prepare_hdiffpatch.py` 固定工具归档与执行文件哈希；Sparkle 构建使用已核对哈希的原始发行归档重新展开，保留框架链接。程序、更新 helper 和安装器随附 `update-codec-notices.txt`。模型打包脚本把 `docling-model-notices.txt` 作为 `NOTICE.txt` 随资产发送，涵盖 Apache-2.0 和 CDLA-Permissive-2.0；模型权重继续适用各自上游条件。旧模型复制只接受可信清单中的字节，新导入目录补入随附声明。模型身份由权重清单决定，展示声明不改变权重身份；资产哈希仍绑定整个 ZIP。旧的本地无声明资产可读取，新生成资产包含声明。

安装器和应用内更新使用共同的验证、下载和组装实现。下载缓存按 SHA256 命名；只有稳定 ETag 才允许 If-Range 续传，完成后重新核对大小与哈希。离线模式读取用户指定签名清单及本地匹配资产，不以网络兜底掩盖缺文件。准备阶段可取消并保留已验证下载，替换阶段通过持久日志恢复。

候选在正常退出当前应用前准备完成。安装事务取得更新锁及实例锁，保存真实 SQLite 快照，写日志后替换程序；新程序以暂停处理的握手启动。版本、首页和文档组件就绪检查成功后，先记录 accepted，再放行任务。失败恢复先还原数据库，再恢复可启动的旧程序路径；已 accepted 的记录只能完成握手和清理，不能再用旧数据库覆盖后续工作。未完成日志阻止普通启动处理数据，并提供安装器恢复入口。安装器不会强杀正在处理用户任务的应用。

Docling 模型可从旧应用资源逐字节复制，或者从独立资产导入。损坏或缺失不自动下载，启动和文档处理明确显示不可用状态。Windows 内部模型文件操作使用扩展路径，避免要求用户修改系统长路径策略；该转换不解析 junction，原有链接与重解析点检查继续执行。

构建入口为 `scripts/build_component_installer.py`、平台原生构建脚本、`scripts/package_docling_component.py` 和 `scripts/prepare_component_release.py`。签发只生成本地清单，不自动上传或切换 Latest。签发前核对实际目标程序、源码及资产字节；安装器的新装、旧版升级、失败恢复、离线流程、完整双平台运行、旧客户端过渡入口及线上签名验证仍是独立发布门禁。

Windows 程序目录切换复用原更新器的有界句柄释放等待；持续占用时保留事务日志及旧副本，供安装器恢复。组件状态、更新计划、安装日志和版本 JSON 明确按 UTF-8 读取，避免系统默认编码使中文路径的恢复或更新失败。

共用模型 ZIP 的许可声明采用 LF 规范字节；该来源文件通过 Git 属性固定 LF，运行时也消除 Windows 检出产生的 CRLF 差异。导入仍严格核对规范声明的大小与哈希，不能以允许换行差异为由接受内容篡改。跨平台发行须实际验证空模型目录的新装，旧版模型复用不能覆盖这个入口。

已知限制：成功安装后，本次组装基座和候选的临时目录尚未自动清理，可能继续占用数 GB；此项已由用户移至下一轮 bug 迭代，见 [BUG-20260914-01](../roadmap/next-version.md#bug-20260914-01成功安装后的临时组装副本清理)。下载缓存用于复用，不能与这些副本一概删除。

## V1.3 安装接受与本次副本退役（施工实现）

事务持久 accepted 与启动放行、事务收尾、组装清理、桌面入口分开返回。
accepted 写入返回异常时先读回日志；身份或持久状态无法核实则保留材料，禁止盲目回退。
进程中断保留日志；普通 accepted 后附属错误返回 pending，不用旧数据库覆盖新数据。
握手写出后必须观察相同实例退出 installing 才标 activation ready。

组装根由独占 mkdir 创建，清理资格只存在创建进程内，绑定候选身份；两入口经
`finalize_install` 调用同一清理边界。只清本次 accepted 且放行已证的 attempt，
缓存/模型/其他 attempt 不扫描。跨进程恢复仍仅补放行及既有事务收尾。
POSIX 删除采用目录描述符及 inode/device 核对；合法 bundle 符号链接只 unlink 目录项。
Windows 祖先和根持 GENERIC_READ 且不共享 DELETE 的句柄；仅 READ_ATTRIBUTES
实测不能阻止 rename，因此权限不足时不能静默降级。内部重解析点保留；普通文件与
目录通过句柄删除，长路径使用扩展路径。占用导致 pending，可在原进程资格有效时重试。
逻辑删除字节按硬链接身份去重，不代表卷可用空间的实际增长。此段描述源码协议，
最终双平台冻结安装器、真实旧版迁移与 UI 门仍须按本轮候选独立验收。
