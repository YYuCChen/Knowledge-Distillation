# V3.0 施工包：统一知识整理与 Obsidian 呈现

状态：**开工前准备稿已完成，尚未授权业务代码施工或正式 Vault 改动。V3.0 将在新的独立 Codex 对话／任务中开发，不在编写本施工包的对话中继续。** “V3.0”是下一大版本的暂定名称；开始施工前按第八部分完成用户确认。本计划依据 [F-11、F-12](next-version.md#f-11统一-local-web开始整理与-vault-wiki-整理入口)、[跨 Agent 交接规则](../engineering/agent-collaboration.md)和根 [`AGENTS.md`](../../AGENTS.md) 的 V3.0 最高施工编排规则编写。

## 一、目标与完成标准

### 1.1 产品目标

把当前两个“整理”收束成一条用户能理解、系统能恢复的主流程：

```text
投递／随手记 → raw/ 正本 → Local Web「开始整理」
                              ↓
                    独立 wiki 维护任务
                              ↓
                   wiki/ 派生知识 + 待确认
                              ↓
                     Obsidian 阅读与确认
```

- `raw/` 继续是不可变素材正本，`wiki/` 成为新的派生知识权威。
- Local Web 是统一启动入口、状态面板和结果入口，不再同时生成另一套会漂移的 Topic／新知结果。
- Claudian 或其他 Agent 的手动维护入口继续存在，但和 Local Web 调用同一套 vault-kit 规则、批次边界、检查和互斥机制。
- 新 wiki 页面、系统页和侧栏呈现继承既有 Obsidian 阅读版的视觉语言，不再像一套外挂的工程目录。

### 1.2 “完成”必须同时满足

1. 点击一次“开始整理”会处理当次冻结的全部待处理素材；内部仍按约 5 份分批，优先本人自述及其关联材料，但 5 份不是总量上限。
2. 任务可显示排队、运行、成功、失败和需要用户处理的真实状态；重复点击、应用重启、Agent 中断或模型失败都不会制造第二套任务、损坏 raw 或覆盖用户编辑。
3. 每个已发布批次都经过 `kb.py` 检查；素材和候选都清零时，按既有规则完成首次体检。失败批次可以从确定边界继续，不要求重做已验证批次。
4. 旧 SQLite Topic、新知和用户判断在迁移完成前只读保留；没有用户确认的语义映射，不删除、不覆盖、不伪装成已经迁入 wiki。
5. 代表性 wiki 页面和系统页在真实 Obsidian 中通过用户视觉确认；样式可关闭、可回退，样式前后内容、证据、链接和编号完全一致。
6. macOS 候选包、V2.0 升级副本、独立测试 Vault、失败恢复和全量回归通过；正式安装、正式 Vault 运行和发行仍分别取得用户授权。

## 三、已经确认的产品边界

- 只维护 macOS；Windows 停留在 V1.3，不进入 V3.0 代码、构建或验收门禁。
- raw 只进不改；稳定编号、段落锚点、来源归属和证据不能因整理或排版变化而改变。
- 确认清单里的“对／改成／不对”及理由不另存为 `raw/自述/`。
- 每批优先处理自述、附言及关联材料；约 5 份只是 Agent 工作单元。
- 首次完整体检在待处理素材和待确认候选都清零后运行；以后有变更时按需运行，通常每周至多一次。
- 已定稿 Local Web UI 的改变必须基于设计母版，先出样稿并由用户确认；不能借统一后台之名自行改版。
- Obsidian 视觉以正式 Vault 的实际配置、既有 `kd-reading.css` 和[阅读阶段结论](../history/2026-09-project-memory/obsidian-reading.md)共同为基线；旧记录不能替代开工时的真实核对。
- 正式数据、正式 Vault、安装前备份和不可再生用户判断继续受现有保护规则约束。

## 四、推荐架构

### 4.1 新建 wiki 维护域，不改造旧整理事件

现有 `organization_events` 及其 coverage、Topic 和新知表记录的是 V1 的 SQLite 整理历史，并有不可删除／不可更新约束。V3.0 不复用或改写这些表。

新增独立的 wiki 维护任务及条目记录，职责至少包括：任务身份、触发来源、冻结边界、vault 身份、vault-kit 版本、Agent 后端和模型、阶段状态、批次进度、检查结果、失败码及恢复状态。数据库只保存路径身份、摘要和计数，不保存真实素材正文、完整模型响应或密钥。

建议状态：`queued → preparing → running → validating → publishing → succeeded`，失败区分可重试失败、配置／登录缺失、并发占用、Vault 在运行中被修改、检查失败和发布恢复失败。页面只显示用户可理解的结果，不暴露内部状态名。

### 4.2 独立 worker 与冻结边界

wiki Agent 运行可能持续数分钟，不能占住现有单 worker，阻塞投递、飞书和来源蒸馏。为 wiki 维护使用独立 worker／子进程生命周期。

任务开始时冻结当时待处理 raw 的确切路径和字节摘要，并按“自述及关联优先、再按时间补足外部素材”生成批次清单。运行期间新写入的 raw 留给下一次任务，不把任务变成没有终点的追赶循环。相同冻结边界的重复点击只复用原任务。

### 4.3 Agent runner

建立工具中立的 `WikiAgentRunner` 边界，首个正式实现建议使用本机 Codex 登录和 Codex CLI，因为 V2.0 已有可核对的可执行文件发现、账号探针和模型选择能力。runner 不提取 Codex token，不回退到未经用户配置的 API key，也不因连接失败偷偷启动旧 SQLite 整理。

每个批次由 runner 在 Vault 规则作用域内执行明确清单，而不是只发送一句模糊的“整理全部”。批次结束必须运行 `kb.py`；只有检查通过，协调器才把它计为完成并进入下一批。模型上下文不足时从下一批继续，不把部分响应当成完整交付。

Claudian 手动入口仍可用。vault-kit 的技能在开工前增加共享运行锁检查，使 Local Web、Claudian、命令行 Agent 三个入口不会同时修改 wiki。

### 4.4 隔离执行、发布与恢复

应用触发的 Agent 不直接在正式 wiki 上边生成边试错。推荐流程：

1. 只读核对 Vault、raw 和当前 wiki，创建本次可恢复备份与发布清单；
2. 在独立 staging Vault 中复制规则、冻结 raw、wiki 和图谱状态；
3. Agent 只在 staging 中修改允许范围；完成后验证 raw 字节未变、路径未越界、`kb.py` 零错误；
4. 发布前再次核对正式 wiki 的预期文件摘要。若用户或其他 Agent 在运行中改过目标，停止发布并提示重新整理，不能覆盖；
5. 按清单逐文件原子替换，保留发布日志；中断时恢复到发布前一致状态；
6. 读回正式 Vault 再判定成功。

允许写入的业务范围仅为 `wiki/`、可再生图谱状态和本次明确拥有的 vault-kit 文件。`raw/`、旧阅读版 `知识蒸馏器/`、附件、其他个人笔记和 `.obsidian` 的非本产品配置都不允许由 Agent 任意改写。

staging 和恢复副本放在本任务拥有、权限受限的本地运行目录，不进入仓库、公开日志或云盘。成功发布并过恢复窗口后清理可重建副本；失败时只保留完成恢复所必需的最小副本和期限，不能让每次整理永久复制一整套私人知识库。

### 4.5 vault-kit 版本与升级

为 vault-kit 增加明确版本和拥有文件清单。应用运行前核对工具包兼容性；升级只替换身份仍匹配的 kit 自有文件，并保留恢复副本，不能覆盖 wiki 内容或用户修改过的未知文件。版本不匹配时先显示修复入口，不用旧规则继续写新格式。

样式资产也纳入 kit 清单，但启用／替换 Obsidian snippet 属于独立动作。候选阶段先安装到测试 Vault；正式 Vault 等用户确认样稿和备份后再升级。

### 4.6 旧 Topic／新知的退场顺序

1. 先冻结旧“开始整理”的写入口，但旧主题、新知和判断页面继续只读可访问。
2. 在真实数据库的只读副本中清点：来源组织结果、AI 新知、用户分类判断、用户原话／追加想法及其谱系；不只统计表行数。
3. 对不可再生用户内容制作脱敏映射样稿，区分用户原话、操作动作、AI 推断和纯机器状态。
4. 用户确认映射后才迁移；逐项对账、可重复运行、失败回退。
5. 迁移和一段观察期通过后，再单独决定是否从日常导航隐藏旧页面。物理删除不属于默认范围。

### 4.7 Local Web 呈现

保留“开始整理”作为一个直接动作，不增加主题、算法或批量参数。页面至少需要表达：待整理素材数、是否正在整理、完成了多少批、是否产生待确认、失败后能做什么，以及进入 Obsidian `wiki/待确认.md`／`wiki/index.md` 的入口。

按钮、状态和结果区先在设计母版中出稿。优先复用现有按钮和状态样式，不新增管理后台式页面；没有真实进度证据时不显示百分比或预计时间。

### 4.8 Obsidian 呈现

- 使用独立、可关闭的 `kd-wiki` 样式作用域，并按页面类型增加稳定 class；不把所有 Markdown 全局改样式。
- 为来源、概念、认知、方法、技能、实践、综合、主题和四类系统页分别定义必要差异，同时继承旧阅读版的主栏宽度、字体、颜色、链接和证据层级。
- 属性仍保留在 Markdown 中，但日常阅读不让通用属性面板压过正文；重要状态在页面模板中有清晰、非重复的阅读位置。
- `raw/`、skills、tools、AGENTS、CLAUDE 是运行接口，不改路径。建议在侧栏里弱化而非完全隐藏，并把 `wiki/index.md` 作为明确的日常入口；最终以用户确认的真实 Obsidian 样稿为准。
- 现有 wiki 页迁移只补样式所需的可逆元数据和模板结构，不改正文语义、证据或链接。

## 五、施工编排、阶段与逐阶段验收

### 5.1 模型职责

根 `AGENTS.md` 是模型分工的唯一权威，施工包不另建一套平行规则。执行摘要如下：

| 角色 | 固定模型 | 固定推理强度 | 责任 |
|---|---|---|---|
| 总控 | `gpt-6-astra` | `medium` | 规划、判断、架构、任务拆分、风险和边界、复核、验收与用户沟通 |
| 开发子 Agent | `gpt-5.6-sol` | `xhigh` | 业务代码、迁移、测试、构建脚本、样式实现和需要技术语义判断的修复 |
| 走查／机械子 Agent | `gpt-5.6-luna` | `max` | 只读走查、定位、清点、归集、重复核对和按精确规则机械写入 |

总控为每个子任务指定互不冲突的文件或职责所有权，并亲自读取实际结果。Luna 遇到歧义立即回报，不能代替 Astra 作判断或代替 Sol 作实质开发；Sol 遇到产品方向、不可逆数据规则或外部操作决定时交回 Astra。指定模型／档位不可用时暂停相关工作，不静默换模型。

## 六、测试与验收矩阵

### 6.1 自动化硬门禁

- 任务唯一性：多次点击、多标签、多个应用进程和 Claudian 并发只能有一个写任务。
- 边界稳定：冻结 60+ 份素材可跨批完成；中途新增素材留到下一任务；本人自述和关联材料优先。
- 幂等与恢复：批次成功后崩溃、验证后崩溃、发布中断、应用重启都能继续或恢复，不能重复生成页面。
- 安全：提示注入素材、符号链接、路径穿越、raw 改写、Vault 外写入和 kit 身份漂移必须被拒绝。
- 并发编辑：正式目标摘要变化时拒绝发布，不覆盖用户或另一 Agent 的新编辑。
- 知识规则：引用存在、段落锚点有效、确认身份正确、自动区块可再生、图谱和页面一致。
- 隐私：产品日志、数据库事件和错误页面不包含原始正文、模型完整响应、token 或账号资料。
- UI：状态来自持久记录；不显示虚构百分比；失败后按钮和任务状态可恢复。

### 6.2 真实环境验证

- 在独立测试 Vault 中用真实 Codex 登录处理多批合成素材，并真实重启应用。
- 在打包 `.app` 中验证 Codex 可执行文件发现、账号过期、模型不可用和网络中断。
- 在真实 Obsidian 中检查代表性页面、侧栏、跳转、阅读／编辑视图和样式开关。
- 用 V2.0 正式数据的只读副本验证 schema 升级、旧页面只读、判断清点和候选回退。
- 正式 Vault 只在备份、候选验证和用户授权后运行；运行后读回 raw 摘要、wiki 检查、数据库 quick check 和核心数量。

### 6.3 发行门禁

V3.0 继续以 macOS arm64 为唯一正式平台。要求干净源码构建、构建前后源码不变、两次启动、页面探针、deep／strict 签名、公开资产匿名完整下载和 SHA-256 对账。至少覆盖 `.4 → V3.0` 升级与固定基座新装；应用、Application Support 和 Vault 回退必须作为一组验证。

## 七、明确不进入本轮的事项

- Windows 或 Intel Mac 支持；
- 通用知识库问答、自动代用户执行业务任务、团队协作或跨设备同步；
- 定时自动整理。V3.0 先保持用户主动触发；
- 无映射地删除旧 Topic／新知／判断，或把 AI 新知直接写成用户认知；
- 移动／重命名 raw、skills、tools、AGENTS、CLAUDE 来美化侧栏；
- 把所有历史小 bug 都塞进 V3.0。成功安装后的临时副本清理等独立待办继续单列，只有直接影响本施工链时才并入；
- 未经用户确认的 Local Web 全面改版或 Obsidian 全局主题替换。
