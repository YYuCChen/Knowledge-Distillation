# 二期施工计划

状态：待开工。依据：[决策0004](../decisions/0004-phase2-alignment.md)、[raw 接口规格](../engineering/raw-interface.md)、[个人知识系统方案](../product/phase2-knowledge-system.md)。执行者：Claude Code，在本机项目目录 `知识蒸馏器/V1.3开发-20260914/source`，分支 `phase2/foundation`。

本计划分两段执行：**开工前准备**（与用户一起完成），然后是**无人值守施工**（用户离开电脑）。

---

## 第一部分：工作方式（必读）

### 1.1 两段式执行

1. **开工前准备（有人值守）**
   - 先完成第二部分的全部检查，把需要的权限、账号、决定、用户协助一次性列给用户，逐项处理完。
   - 用户确认"可以离开"之后，才进入施工。
   - 准备阶段不写业务代码。
2. **无人值守施工**
   - 用户离开电脑，不再回答问题，也不会点任何授权弹窗。
   - 按第三部分的顺序，**以最优路径一直干到交付**。

### 1.2 施工期的硬规则

- **不妥协。** 不得因为权限、授权、环境不便，改走次优路径或降级方案；不得放宽来源真实性、完整性、测试门禁；不得用 mock 冒充真实运行证据。
- **碰到准备阶段没清掉的阻塞时：**
  - 不停工，也不绕路。把该项标为"阻塞"，写明原因、已做的部分，以及用户回来后要做的一步操作。
  - 然后继续其他不依赖它的工作。
  - 所有阻塞在最终交付报告里集中列出。
- **不打扰。** 不发起需要用户在场才能完成的操作。准备阶段已获授权的范围内可以直接做，范围外的一律视为阻塞。
- **不越界。**
  - 正式应用 `/Applications/知识蒸馏器.app`、正式数据目录（`~/Library/Application Support/Knowledge Distiller/`）、正式 Vault：除非准备阶段用户明确授权，否则一律不碰。
  - 测试一律使用独立、可丢弃的数据目录和测试 vault。
- **不删用户的东西。** 只清理本任务自己创建、确认可重建的临时产物。
- **遵守两份仓库级规则：**
  - [AGENTS.md](../../AGENTS.md)，包括最高工作原则和定稿 UI 保护；
  - 本地 `~/Documents/知识蒸馏器/项目治理/V1.3使用期Bug归纳与二期Mac收尾交接-20260928.md` 第六、七、八节中的测试纪律与交付证据要求。
- **及时落档。** 每完成一个阶段就提交一次，提交信息写清改动和验证；并更新第五部分的进度表。

## 第三部分：无人值守施工

每个阶段结束都要满足该阶段的验收，并单独提交。阶段之间没有依赖的，可以按最优顺序调整。

### 第 0 阶段：V1.3 收尾（仅 macOS）

依据交接文档第四、五节。先在本分支找到对应实现，不要照搬旧行号。

| 项目 | 要求 |
|---|---|
| BUG-20260922-01 X 图片 OCR | Vision options 修正；拆分诊断阶段；正式 `.app` 冒烟 |
| BUG-20260922-02 抖音登录状态 | 设置页实时、非破坏性校验；过期映射为 `douyin_login_required`；拆分内部子码；重连后同一短链接完整处理且不重复生成知识 |
| BUG-20260916-01 整理按钮 | 请求被接受的同时真正禁用；验证 `start_or_reuse()` 幂等；不改样式和文案 |
| BUG-20260916-02 整理失败提示 | 当次页面可见，刷新后消失；保留历史与诊断；与上一条分别验收 |
| BUG-20260915-02 文档模型提示 | 轮询状态同步到静态提示；不改完整性校验 |
| BUG-20260917-01 | 补齐脱敏诊断子码，不改定稿 UI；无证据不盲修 |
| Dock | 仅在 Q1 已选时按所选方案做；否则跳过 |
| Q9 | 核对后处理 |

**验收**：每项附交接文档第七节的 7 项证据；系统边界项必须在正式 `.app` 上运行过；注明"Windows 未测、未构建、未维护"。

### 第 1 阶段：应用写 raw

按 raw 接口规格第 1～7 节实现。

- 外部素材在 `source_facts` 生成后写入 raw。
- 数据库记录编号与路径的映射；做到原子写入、不覆盖、支持 vault 恢复后补写、支持取代写法。
- 存量迁移工具：可重复执行，结果一致；只新建文件。
- 设置页如需新增开关或状态（例如"写入 raw"），必须沿用设计母版的现有组件；如果需要新的界面样式，视为定稿 UI 改动，先不做，记入待确认。
- **验收**：规格第 9 节应用侧全部场景；在复制出的数据副本和测试 vault 上完整跑一遍迁移。

### 第 2 阶段：飞书随手记

按飞书随手记需求（除 4.4 外全部）和 raw 接口规格 5.2 实现。

- 接入语音附件，复用现有 ASR。
- 身份判定：先走规则，再走可替换的判断接口；提供云端判断开关。
- 身份待定的消息进入现有待办样式。
- 疑点订正保留原识别。
- 邻接记录只记"之前"一侧。
- 录音在疑点处理完后释放。
- **验收**：需求第 6 节的全部合成场景。真实飞书收发如果未能在准备阶段完成，列入用户回来后的验收清单，不得用合成测试冒充。

### 第 3 阶段：vault-kit 适配与端到端

按 raw 接口规格第 8 节改造 `vault-kit/`：

- kb.py 支持段落引用；新增 `raw-id` 子命令，能读取 raw 信封。
- 按规格修订守则，并加入同名异义的括注规则。
- vault 根目录新增 CLAUDE.md。
- 为 Codex（经 Claudian 使用）提供四个快捷命令：处理新素材、体检、确认、陪读。放在 Claudian 或 Codex 实际读取的位置，以 2.2 查实的方式为准。

然后在测试 vault 上用第 1、2 阶段产生的 raw，**用真实 Codex CLI** 完整跑一遍"处理新素材 → 查看待确认 → 模拟确认 → 体检"，确认 kb.py 检查无错误。

- **验收**：kb.py 的单元测试；端到端运行记录（Codex 的输入与输出摘要、kb.py 检查结果）。

### 第 4 阶段：集成与交付

- 全量测试；构建正式候选 `.app`，并在独立位置用数据副本做升级可读性验证。
- 更新 README 的开发说明与 `docs/` 入口；在 `docs/roadmap/next-version.md` 更新 bug 状态。
- 推送分支并开 PR（仅限 P4 已授权）。
- 写交付报告（第四部分）。

## 第四部分：交付报告格式

写在 `docs/releases/phase2/delivery.md`：

1. 完成了什么：逐阶段、逐项列出，并附验收证据位置。
2. 做了哪些可逆的取舍，哪些不可逆的决定按规格执行了。
3. **阻塞清单**：每项写明原因、已完成的部分、用户要做的一步操作。
4. **用户回来后的验收清单**：
   - 真实飞书收发；
   - 正式 Vault 迁移命令；
   - 在 Obsidian 里用 Claudian 试一次"处理新素材"；
   - 候选 `.app` 的安装方式；
   - 以及其他只有用户能做的事。
5. 未验证项与剩余风险；Windows 冻结说明。
